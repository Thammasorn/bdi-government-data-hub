เอกสารนี้ขยายสเปกใน Notion ให้ครบพอที่จะลงมือพัฒนาได้ ส่วนที่ Notion ยังไม่ได้ระบุจะทำเครื่องหมาย
**[สมมติฐาน]** ไว้ และรวบรวมไว้ท้ายเอกสารเพื่อให้ยืนยันภายหลัง

## 1. Roles

| Role | รหัสในระบบ | ขอบเขต | หน้าที่ในสองเส้นทางนี้ |
| --- | --- | --- | --- |
| BDI Officer | `BDI_OFFICER` | ทั้งระบบ | ตรวจสอบข้อมูลหน่วยงานที่ยื่นเข้ามา อนุมัติหรือส่งกลับให้แก้ |
| BDI Approver | `BDI_APPROVER` | ทั้งระบบ | เห็นชอบและลงนามขั้นสุดท้าย ทำให้หน่วยงานเปิดใช้งาน |
| BDI Specialist | `BDI_SPECIALIST` | ทั้งระบบ | ยังไม่มีบทบาทในสองเส้นทางนี้ (มีไว้ใน invite API ตามสเปก) |
| Organization User | `ORG_USER` | หน่วยงานตนเอง | กรอกและนำส่งฟอร์มสร้างหน่วยงาน |
| Organization Approver | `ORG_APPROVER` | หน่วยงานตนเอง | ผู้มีอำนาจกระทำการแทน — ตรวจ PDF และให้ความเห็นชอบ |

> **[สมมติฐาน]** ผู้ใช้หนึ่งคนมีได้หลาย role และ role ผูกกับหน่วยงาน (สำหรับ `ORG_*`)
> ตอบคำถามที่ค้างใน Notion ว่า *"มี user หลายคนในหน่วยงานเดียวกันได้ไหม"* → **ได้**
> โดยหน่วยงานหนึ่งมี `ORG_USER` ได้หลายคน แต่มี `ORG_APPROVER` ที่ลงนามได้ตามที่ระบุในฟอร์ม

## 2. Journey A — Admin Create New User

สเปกระบุชัดว่า **ขั้นตอนเชิญเป็น API ล้วน ไม่มี UI** แต่ต้องเตรียม API ไว้

```
Admin (นอกระบบ)  ──คุยกับหน่วยงาน──▶  ตัดสินใจว่าจะเชิญใคร
        │
        ▼  POST /api/admin/invitations   (x-admin-token)
   ┌────────────────┐
   │  Invitation    │  status = PENDING, token, expiresAt (7 วัน)
   └────────────────┘
        │  ส่งอีเมลเชิญ
        ▼
   ผู้ถูกเชิญเปิดลิงก์  /register?token=...
        │
        ▼  กรอกชื่อ-สกุล, เบอร์โทร, ตั้งรหัสผ่าน
        ▼  ยืนยันตัวตนสองชั้น (2FA)
   ┌────────────────┐
   │  User          │  status = ACTIVE, role ตามที่ระบุตอนเชิญ
   └────────────────┘  Invitation → ACCEPTED
```

### A.1 API เชิญผู้ใช้

```http
POST /api/admin/invitations
x-admin-token: <ADMIN_API_TOKEN>
Content-Type: application/json

{ "email": "somchai@moph.go.th", "role": "ORGANIZATION_USER" }
```

- `role` เลือกได้: `BDI_OFFICER` · `BDI_APPROVER` · `BDI_SPECIALIST` · `ORGANIZATION_USER` · `ORGANIZATION_APPROVER`
- ตรวจ format อีเมล และกันเชิญซ้ำ (ถ้ามี invitation ที่ยัง `PENDING` อยู่ → ออก token ใหม่แทนที่ของเดิม)
- ถ้าอีเมลนี้เป็น user อยู่แล้ว → `409` พร้อมบอกว่ามีบัญชีแล้ว
- ตอบกลับ `201` พร้อม `invitationId`, `expiresAt` (ไม่คืน token ใน response — token อยู่ในอีเมลเท่านั้น)

### A.2 การสมัครและ 2FA

สเปกระบุ *"ระหว่างการสมัครต้องมี two factor authen ด้วย email หรือ ThaiD"*

| ช่องทาง | สถานะการพัฒนา |
| --- | --- |
| **Email OTP** | ทำจริงในเฟสนี้ — ส่งรหัส 6 หลัก อายุ 10 นาที ขอใหม่ได้ทุก 60 วินาที |
| **ThaiD** | เตรียม `AuthProvider` interface + ปุ่มในหน้า UI ที่ยัง disabled — ต้องใช้ OAuth client จริงจาก ThaiD ซึ่งยังไม่มี |

ขั้นตอน:

1. เปิดลิงก์เชิญ → ระบบตรวจ token (ยังไม่หมดอายุ ยังไม่ถูกใช้)
2. หน้าสมัครแสดงอีเมลที่ถูกเชิญแบบอ่านอย่างเดียว (แก้ไม่ได้ กัน invite ถูกใช้ผิดคน)
3. กรอก คำนำหน้า / ชื่อ / นามสกุล / เบอร์โทร / รหัสผ่าน (ต้อง ≥ 8 ตัว มีตัวเลขและตัวอักษร)
4. กด "ถัดไป" → ระบบส่ง OTP ไปที่อีเมลนั้น
5. กรอก OTP 6 หลัก → ผ่านแล้วสร้าง `User` (`emailVerifiedAt` = now) และ mark invitation เป็น `ACCEPTED`
6. ล็อกอินอัตโนมัติ แล้วพาไปหน้าแรกตาม role

> **[สมมติฐาน]** ผิด OTP เกิน 5 ครั้ง → invalidate รหัสนั้น ต้องกดขอใหม่

## 3. Journey B — สร้างหน่วยงาน

### 3.1 State machine ของหน่วยงาน

สถานะทั้งสี่มาจาก Notion โดยตรง เพิ่ม `DRAFT` เข้ามาเพราะสเปกมีปุ่ม "บันทึกแบบร่าง"

```
        ┌─────────┐
        │  DRAFT  │  ผู้ใช้หน่วยงานกำลังกรอก (ยังไม่ส่ง)
        └────┬────┘
             │ นำส่งฟอร์มสร้างหน่วยงาน
             ▼
   ┌──────────────────────┐        ต้องปรับปรุง       ┌──────────────────┐
   │  PENDING_BDI_REVIEW  │ ───────────────────────▶ │  NEEDS_REVISION  │
   │  รอตรวจสอบจาก BDI    │ ◀─────────────────────── │  รอการแก้ไข       │
   └──────────┬───────────┘        แก้แล้วส่งใหม่      └──────────────────┘
              │ BDI Officer อนุมัติ
              ▼
   ┌────────────────────────────┐
   │  PENDING_SIGNATORY_REVIEW  │  รอตรวจสอบจากผู้มีอำนาจ
   └──────────┬─────────────────┘
              │ ผู้มีอำนาจกระทำการแทน เห็นชอบ
              ▼
   ┌──────────────────────────┐
   │  PENDING_BDI_APPROVAL    │  รอ BDI Approver ลงนาม
   └──────────┬───────────────┘
              │ BDI Approver เห็นชอบและลงนาม
              ▼
        ┌──────────┐
        │  ACTIVE  │  เปิดใช้งาน
        └──────────┘
```

ทุกครั้งที่สถานะเปลี่ยน บันทึกลง `OrganizationEvent` (ใคร ทำอะไร เมื่อไหร่ หมายเหตุอะไร)
เพื่อให้แสดง timeline ได้และตรวจสอบย้อนหลังได้

> **[สมมติฐาน]** `NEEDS_REVISION` จากผู้มีอำนาจหรือ BDI Approver ก็ส่งกลับมาที่ `NEEDS_REVISION` เหมือนกัน
> และเมื่อผู้ใช้แก้แล้วส่งใหม่ จะกลับไปเริ่มที่ `PENDING_BDI_REVIEW` เสมอ

### 3.2 ขั้นตอนที่ 1 — ผู้ใช้จากหน่วยงานกรอกข้อมูล

1. ผู้ใช้ role `ORG_USER` ที่ยังไม่มีหน่วยงาน ล็อกอินเข้ามา
2. หน้าแรกแสดง **empty state กลางจอ** พร้อมปุ่ม `สร้างหน่วยงาน` — เป็นเมนูเดียวที่เห็นและกดได้
   (เมนูอื่นซ่อนทั้งหมดตามสเปก)
3. ฟอร์มแบ่งสามส่วนตามภาพในสเปก:

**ส่วนที่ 1 — ข้อมูลหน่วยงาน**

| ฟิลด์ | ชนิด | การตรวจสอบ |
| --- | --- | --- |
| ชื่อหน่วยงาน | free text | บังคับ, 3–200 ตัวอักษร |
| ที่อยู่ (บ้านเลขที่/ถนน) | free text | บังคับ |
| จังหวัด | dropdown | บังคับ, 77 จังหวัด |
| อำเภอ/เขต | dropdown | บังคับ, กรองตามจังหวัด |
| ตำบล/แขวง | dropdown | บังคับ, กรองตามอำเภอ |
| รหัสไปรษณีย์ | text | บังคับ, 5 หลัก **[สมมติฐาน]** เติมอัตโนมัติจากตำบล |
| อีเมลหน่วยงาน | free text | บังคับ, ตรวจ format |

**ส่วนที่ 2 — ผู้มีอำนาจกระทำการแทน**

| ฟิลด์ | ชนิด | การตรวจสอบ |
| --- | --- | --- |
| คำนำหน้า | dropdown | บังคับ |
| ชื่อ-นามสกุล | free text | บังคับ |
| ตำแหน่ง | free text | บังคับ |
| อีเมล | free text | บังคับ, ตรวจ format — **อีเมลนี้จะถูกใช้เชิญเข้าระบบ** |
| เลขบัตรประชาชน | ตัวเลข 13 หลัก | บังคับ, ตรวจ checksum ตามมาตรฐานไทย |
| เบอร์โทรศัพท์ | free text | บังคับ, ตรวจรูปแบบเบอร์ไทย |
| คำสั่งแต่งตั้งผู้มีอำนาจกระทำการแทน | ไฟล์ pdf/jpg | **บังคับ**, ≤ 10 MB |
| คำสั่งมอบอำนาจ | ไฟล์ pdf/jpg | ไม่บังคับ, ≤ 10 MB |

**ส่วนที่ 3 — ผู้กรอกข้อมูล**

| ฟิลด์ | ชนิด | การตรวจสอบ |
| --- | --- | --- |
| คำนำหน้า | dropdown | บังคับ |
| ชื่อ-นามสกุล | free text | บังคับ |
| ตำแหน่ง | free text | บังคับ |
| ฝ่าย/กอง/สำนัก | free text | บังคับ |
| อีเมล | free text | บังคับ, ตรวจ format |
| เบอร์โทรศัพท์ | free text | บังคับ, ตรวจรูปแบบ |

> สเปกใน Notion ระบุ "ตำแหน่ง" ซ้ำสองครั้งในส่วนที่ 3 — ตีความว่าเป็นความซ้ำซ้อนในการเขียน
> จึงเก็บ **ตำแหน่ง** กับ **ฝ่าย/กอง/สำนัก** อย่างละหนึ่งช่อง **[สมมติฐาน]**

4. ปุ่ม `บันทึกแบบร่าง` — ตรวจข้อมูลเบื้องต้น ถ้าไม่ผ่านแสดง **toast เตือน** ตามสเปก
   และไฮไลต์ช่องที่ผิดพร้อมข้อความใต้ช่อง
5. เมื่อผ่านการตรวจ ระบบ **สร้าง PDF จาก template** โดยเติมข้อมูลที่กรอก แล้วแสดงให้ผู้ใช้ตรวจ
   (แสดงแบบฝัง preview เต็มหน้า พร้อมปุ่มดาวน์โหลด)
6. ผู้ใช้กด `นำส่งฟอร์มสร้างหน่วยงาน`
7. ระบบบันทึก, เปลี่ยนสถานะเป็น `PENDING_BDI_REVIEW`, ส่งอีเมลแจ้ง BDI Officer ทุกคน
8. redirect ไปหน้ารายละเอียดหน่วยงาน ซึ่งแสดงสถานะและ timeline

### 3.3 ขั้นตอนที่ 2 — BDI Officer ตรวจสอบ

1. เมนู **หน่วยงาน** แสดงตารางที่มีคอลัมน์ตามสเปก:
   ชื่อหน่วยงาน · ชื่อผู้สร้าง + อีเมลผู้สร้าง · สถานะ
   พร้อม **filter ได้ทุกคอลัมน์** และค้นหาข้อความ
2. เปิดดูรายละเอียด → เห็นข้อมูลทุกส่วน, ไฟล์แนบ, และ **PDF ที่ generate** แบบฝังในหน้า
3. ปุ่ม `ต้องปรับปรุง` → เปิด **modal** ให้พิมพ์รายละเอียดสิ่งที่ต้องแก้ → ยืนยัน
   → สถานะเป็น `NEEDS_REVISION` + ส่งอีเมลแจ้งเจ้าหน้าที่หน่วยงาน (แนบข้อความที่พิมพ์)
4. ปุ่ม `อนุมัติ` →
   - ถ้าอีเมลผู้มีอำนาจกระทำการแทน **ยังไม่มีในระบบ** → สร้าง invitation role `ORGANIZATION_APPROVER`
     ผูกกับหน่วยงานนี้ แล้วส่งลิงก์สมัคร (เข้าสู่ Journey A)
   - ถ้ามีแล้ว → ผูก role `ORG_APPROVER` ของหน่วยงานนี้ให้ทันที
   - สถานะ → `PENDING_SIGNATORY_REVIEW`, ส่งอีเมลพร้อมรายละเอียดคำขอ

### 3.4 ขั้นตอนที่ 3 — ผู้มีอำนาจกระทำการแทน

1. ล็อกอิน (หรือสมัครผ่านลิงก์ที่ได้รับ) → เห็นรายการที่รอตนเองพิจารณา
2. เปิดดู → รีวิว PDF
3. กด `เห็นชอบ` → สถานะ `PENDING_BDI_APPROVAL` + แจ้ง BDI Approver
   หรือกด `ต้องปรับปรุง` → `NEEDS_REVISION` + แจ้งผู้กรอก

### 3.5 ขั้นตอนที่ 4 — BDI Approver

1. เห็นรายการสถานะ `PENDING_BDI_APPROVAL`
2. รีวิว PDF แล้วกด `เห็นชอบและลงนาม` → สถานะ `ACTIVE`
3. ระบบแจ้งทุกฝ่ายว่าหน่วยงานเปิดใช้งานแล้ว และปลดล็อกเมนูอื่นให้ผู้ใช้ของหน่วยงานนั้น

## 4. อีเมลที่ระบบส่ง

ทั้งหมดส่งผ่าน SMTP (ตั้งค่า Gmail ไว้สำหรับทดสอบ — ดู `.env.example`)

| # | เหตุการณ์ | ถึง | เนื้อหาสำคัญ |
| --- | --- | --- | --- |
| 1 | Admin เชิญผู้ใช้ | ผู้ถูกเชิญ | ลิงก์สมัคร + วันหมดอายุ |
| 2 | ขอรหัส 2FA | ผู้สมัคร | OTP 6 หลัก อายุ 10 นาที |
| 3 | นำส่งฟอร์มหน่วยงาน | BDI Officer ทุกคน | ชื่อหน่วยงาน ผู้ยื่น ลิงก์ตรวจสอบ |
| 4 | BDI ส่งกลับให้แก้ | ผู้กรอกข้อมูล | เหตุผลที่ต้องแก้ + ลิงก์แก้ไข |
| 5 | BDI อนุมัติ | ผู้มีอำนาจกระทำการแทน | รายละเอียดคำขอ + ลิงก์ (พร้อมลิงก์สมัครถ้ายังไม่มีบัญชี) |
| 6 | ผู้มีอำนาจเห็นชอบ | BDI Approver ทุกคน | ลิงก์ลงนาม |
| 7 | เปิดใช้งานหน่วยงาน | ผู้กรอก + ผู้มีอำนาจ | ยืนยันว่าหน่วยงานพร้อมใช้งาน |

ทุกฉบับใช้เทมเพลตเดียวกันตาม CI (โลโก้ BDI, navy `#192768`, ปุ่ม coral `#E5775A`)

## 5. คำถามที่ยังค้าง — ต้องยืนยันกับเจ้าของสเปก

Notion เขียนคำถามเหล่านี้ไว้เอง และผมเพิ่มที่พบระหว่างออกแบบ

1. **ชื่อหน่วยงาน** — Notion ตั้งคำถามว่าควรมีรายการหน่วยงานให้เลือกพร้อมที่อยู่หรือไม่
   ตอนนี้ทำเป็น free text ตามสเปกหลัก แต่โครงสร้าง `Organization.name` รองรับการเปลี่ยนเป็น
   reference ไปยังทะเบียนหน่วยงานภายหลังได้
2. **ผู้ใช้หลายคนต่อหน่วยงาน** — ออกแบบให้ได้ไว้ก่อน (ดูข้อ 1)
3. **ขั้นตอนที่ 2 ข้อ 5 ในสเปกเขียนค้างไว้** ("เมื่อผู้มีอำนาจกระทำการแทน") — ตีความตามข้อ 3.4
4. **การลงนามของ BDI Approver** — สเปกเขียนว่า "ลงนาม" ยังไม่ระบุว่าเป็น digital signature จริง
   หรือแค่กดยืนยัน ตอนนี้ทำเป็นกดยืนยันพร้อมบันทึกผู้ลงนามและเวลาลง audit log
5. **ThaiD** — ยังไม่มี client credentials จึงเตรียมโครงไว้แต่ยังใช้ไม่ได้
6. **PDF template** — สเปกมีภาพตัวอย่างแต่ไม่มีไฟล์ template จริง จึงสร้างเทมเพลตขึ้นใหม่
   ให้ตรงกับโครงสร้างข้อมูลและ CI
