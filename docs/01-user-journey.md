## 2. Journey A — Admin Create New User

สเปกระบุชัดว่า **ขั้นตอนเชิญเป็น API ล้วน ไม่มี UI** แต่ต้องเตรียม API ไว้

```
Admin (นอกระบบ)  ──คุยกับหน่วยงาน──▶  ตัดสินใจว่าจะเชิญใคร
        │
        ▼  POST /api/admin/invitations   (x-admin-token)
   ┌────────────────┐
   │  Invitation    │  status = PENDING, token, expiresAt (7 วัน)
   └────────────────┘
        │  ส่งอีเมลเชิญ
        ▼
   ผู้ถูกเชิญเปิดลิงก์  /activate?token=...   (หรือกรอก key เองจากหน้า login)
        │
        ▼  ยืนยันตัวตนด้วย ThaiD → เทียบ pid กับ cid ที่เจ้าหน้าที่บันทึกไว้
        ▼  กรอกชื่อ-สกุล, เบอร์โทร, ตั้งรหัสผ่าน
   ┌────────────────┐
   │  User          │  status = ACTIVE, role ตามที่ระบุตอนเชิญ
   └────────────────┘  Invitation → ACCEPTED
```

### A.1 API เชิญผู้ใช้

```http
POST /api/admin/invitations
x-admin-token: <ADMIN_API_TOKEN>
Content-Type: application/json

{ "email": "somchai@moph.go.th", "role": "ORGANIZATION_USER", "organizationId": "...",
  "prefixTh": "นาย", "firstnameTh": "สมชาย", "lastnameTh": "ใจดี", "cid": "1234567890121" }
```

- `role` เลือกได้: `BDI_OFFICER` · `BDI_FINAL_APPROVER` · `BDI_DATASET_SPECIALIST` ·
  `BDI_LEGAL_OFFICER` · `SYSTEM_ADMINISTRATOR` · `ORGANIZATION_USER` · `ORGANIZATION_APPROVER`
- `organizationId` **บังคับสำหรับ role ฝั่งหน่วยงาน** (`ORGANIZATION_USER` ·
  `ORGANIZATION_APPROVER`) — ไม่ส่งมาได้ `400` · role ฝั่ง BDI ผูกกับหน่วยงาน BDI ให้เอง
  คนที่จะมาสร้างหน่วยงานของตัวเอง (Journey B) ให้แอดมินสร้างหน่วยงานด้วย
  `POST /api/admin/organizations` ก่อน (บังคับแค่ `organizationCode` กับ `nameTh`)
  แล้วค่อยเชิญด้วย id ที่ได้ — เดิมระบบสร้างหน่วยงานเปล่าให้เอง ซึ่งสร้างใบใหม่ทุกครั้ง
  ที่เชิญและทำให้เหลือลิงก์เปิดใช้งานที่ใช้ได้พร้อมกันสองใบ
- `firstnameTh` · `lastnameTh` **บังคับทุก role** — ชื่อจริงตามเอกสารที่หน่วยงานส่งมา
  ไม่ใช่ชื่อที่แสดง เพราะเอกสาร A0–A3 เลือกชื่อจากสองช่องนี้ก่อน `display_name` เสมอ
  ระบบประกอบ `display_name` จากทั้งสามช่องให้เอง จึงไม่รับ `displayName` มาตรง ๆ อีกแล้ว
- `prefixTh` ไม่บังคับ แต่ควรใส่ — ThaiD **ไม่ส่งคำนำหน้ามาให้** (claim `title` อยู่นอก
  scope ที่กรมการปกครองอนุมัติ ดู `docs/07` §4.1) ค่าที่กรอกที่นี่จึงเป็นตัวเดียวที่ไปเติม
  ช่องคำนำหน้าในฟอร์มเปิดใช้งานของผู้ถูกเชิญ
- `cid` **บังคับทุก role** — เป็นเลขที่ ThaiD จะถูกนำมาเทียบด้วยตอนเปิดใช้งานบัญชี
  (ดู `docs/07-thaid-integration.md` §1) ตรวจ checksum เลขบัตร 13 หลักที่ชั้น zod
- **ไม่มีการเชิญซ้ำ** — อีเมลหรือ `cid` ที่มีบัญชีอยู่แล้ว (สถานะใดก็ตาม) ตอบ `409` เสมอ
  และไม่เขียนทับข้อมูลเดิม คำตอบคืน `activationKeyId` ของใบเดิมมาให้ด้วย เพื่อให้เลือกได้ว่า
  จะส่งลิงก์ใหม่ (`POST /api/admin/invitations/:id/resend`) หรือจะลบแล้วเชิญใหม่
  (`DELETE /api/admin/invitations/:id` ซึ่งคืนทั้งอีเมลและเลขบัตรให้ใช้ใหม่ได้)
- **ส่งลิงก์ซ้ำ** ใช้ `POST /api/admin/invitations/:id/resend` — ไม่รับ payload เลย
  ออกคีย์ใบใหม่บนบัญชี/หน่วยงาน/role เดิม แล้วยกเลิกใบเก่าให้
- **ค้นหาคำเชิญ** `GET /api/admin/invitations?email=&cid=&status=&organizationId=&page=&pageSize=`
  (`email` ค้นบางส่วนได้ · `cid` ต้องตรงตัวเต็ม)
- ตอบกลับ `201` พร้อม `invitationId`, `expiresAt` (ไม่คืน token ใน response — token อยู่ในอีเมลเท่านั้น)

### A.1.1 จัดการบัญชีที่เปิดใช้งานแล้ว — `/api/admin/users`

คำเชิญ (`/api/admin/invitations`) ดูแลบัญชีที่ยัง `PENDING` ส่วนบัญชีที่เข้าระบบไปแล้ว
อยู่ที่นี่ ทั้งชุดใช้ `x-admin-token` เหมือนกัน และยังไม่มีหน้าจอ

**ลบบัญชีที่เปิดใช้งานแล้วไม่ได้** ฐานข้อมูลกันไว้เองด้วย FK สามใบที่เป็น `ON DELETE RESTRICT`
(`legal.legal_acceptance` · `signature.signature_confirmation` · `review.review_task.assigned_user_id`)
"ลบ" ของระบบนี้คือ `DEACTIVATED` ซึ่งเก็บแถวไว้ครบพร้อมอีเมลและเลขบัตร

| Endpoint | ทำอะไร |
| --- | --- |
| `GET /users` | ค้นด้วย `q` (อีเมล/ชื่อ) · `cid` (ตรงตัวเต็ม) · `status` · `role` · `organizationId` + แบ่งหน้า |
| `GET /users/:id` | โปรไฟล์ + ประวัติ role + คำเชิญ + session ที่ยังเปิด + audit ล่าสุด |
| `PATCH /users/:id` | แก้โปรไฟล์ (ชื่อ เบอร์ ตำแหน่ง ฝ่าย) |
| `POST /users/:id/identity` | แก้ `email` / `cid` — แยกออกมาเพราะเป็น identity anchor · ปิด session ทุกใบ |
| `POST /users/:id/suspend` | ระงับชั่วคราว **role ยังอยู่ครบ** · ปิด session |
| `POST /users/:id/reinstate` | คืนสถานะจาก `SUSPENDED` |
| `POST /users/:id/deactivate` | ยุติการใช้งาน · ถอน role ทุกใบ ยกเลิกคำเชิญ ปิด session |
| `POST /users/:id/reactivate` | เปิดกลับจาก `DEACTIVATED` — **ไม่คืน role ให้เอง** |
| `POST /users/:id/release-identity` | ปล่อย **อีเมล** ให้ใช้ใหม่ได้ (บัญชีต้อง `DEACTIVATED` ก่อน) |
| `POST /users/:id/roles` · `DELETE /users/:id/roles/:assignmentId` | มอบ / ถอนสิทธิ์ |
| `POST /users/:id/transfer` | ย้ายหน่วยงาน — ถอนของเดิมและมอบของใหม่ในคำสั่งเดียว |
| `GET`/`DELETE /users/:id/sessions` | ดู / บังคับออกจากระบบทุกเครื่อง |

`reason` **บังคับ** ทุกคำสั่งที่ตัดสิทธิ์คน และถูกบันทึกลง `audit_event` กับแจ้งเจ้าตัว

#### เลขบัตรกับอีเมลเป็นตัวระบุคนละชนิด

`cid` คือ **คน** — ถาวร ไม่ซ้ำทั้งประเทศ **ไม่มีคำสั่งไหนปล่อยคืน** · `email` คือ
**กล่องจดหมาย** ซึ่งเปลี่ยนมือได้จริง จึงปล่อยคืนได้ผ่าน `release-identity` เท่านั้น

ผลคือ *สร้างบัญชีใหม่ด้วยเลขบัตรเดิม* ไม่มีในระบบ คนเดิมที่กลับเข้ามาใช้ `reactivate`
แถวเดิม เพราะ `legal_acceptance` กับ `signature` ชี้มาที่บัญชี ถ้าแตกคนคนเดียวเป็นสองแถว
ระบบจะตอบไม่ได้ว่าใครลงนามเอกสาร A0–A3 ฉบับนั้น

#### หนึ่งบัญชี = หนึ่งหน่วยงาน

บัญชีหนึ่งใบถือ role ระดับหน่วยงานที่ใช้งานอยู่ได้ไม่เกินหนึ่งหน่วยงาน ครอบทั้ง
`ORGANIZATION_USER` และ `ORGANIZATION_APPROVER` และข้ามบทบาทกันด้วย — มอบ role ทับ
จะได้ `409 organization_clash` พร้อมบอกให้ใช้ `transfer` แทน

#### ย้ายหน่วยงานแล้วงานไม่ตามไปด้วย

`transfer` ทำในทรานแซกชันเดียว: ดันงานที่ค้างอยู่กับเขาในหน่วยงานเดิมกลับเป็น `DRAFT`
(ปิด review task เป็น `CANCELLED` · ล้าง `submittedAt` · ล้าง `approverEmail` ถ้าเขาคือ
ผู้มีอำนาจของใบนั้น) → ถอน role เดิม → มอบ role ใหม่ → ปิด session

แล้วแจ้งสองทาง: เจ้าตัว และ**คนที่ยังอยู่กับหน่วยงานเดิม**ว่ามีคนย้ายออกและคำขอกลับเป็นร่าง
ส่วนแอดมินได้รายการคำขอที่ถูกดันกลับและรายชื่อหน่วยงานที่ไม่เหลือผู้รับผิดชอบใน response
— **ย้ายได้เสมอ ไม่บล็อก**

#### คำขอเป็นของหน่วยงาน ไม่ใช่ของคนที่กดสร้าง

เกณฑ์แก้และนำส่งคำขอจดทะเบียนคือ "เป็นผู้ดำเนินการที่ใช้งานอยู่ของหน่วยงานเจ้าของคำขอ"
ไม่ใช่ `created_by` อีกแล้ว ถ้ายังผูกกับคนสร้าง คำขอที่ถูกดันกลับเป็นร่างจะแก้ได้โดย
คนที่ย้ายออกไปแล้วเท่านั้น ส่วนคนที่ยังอยู่จะได้ 404

#### ชื่อที่เติมให้ตอนเปิดใช้งาน มาจากไหนก่อน

```
prefix    = ThaiD title       ?? ค่าจากคำเชิญ     (title อยู่นอก scope — ตกมาที่คำเชิญเสมอ)
firstName = ThaiD given_name  ?? ค่าจากคำเชิญ
lastName  = ThaiD family_name ?? ค่าจากคำเชิญ
```

`given_name` / `family_name` อยู่ใน scope ที่ได้รับแล้ว เคสปกติจึงเติมจากบัตร ส่วนค่าจาก
คำเชิญได้ใช้จริงเมื่อ ThaiD ไม่ได้ทำงาน — โหมด `THAID_BYPASS=true` (ที่ SIT ใช้อยู่) ·
ยังไม่ได้ตั้งค่า ThaiD · หรือกรมการปกครองส่ง claim มาเป็นค่าว่าง

ทุกช่องยังแก้ได้เอง — เป็นค่าตั้งต้น ไม่ใช่การล็อก

### A.2 การสมัครและ 2FA

สเปกระบุ *"ระหว่างการสมัครต้องมี two factor authen ด้วย email หรือ ThaiD"*
การ์ด **ThaiD Integration** (2026-08-13) ตัดสินให้ขั้นเปิดใช้งานบัญชีใช้ ThaiD ทางเดียว
ส่วน Email OTP ย้ายไปเป็นชั้นที่สองของการ **เข้าสู่ระบบด้วยรหัสผ่าน**

| ช่องทาง | ใช้ที่ไหน |
| --- | --- |
| **ThaiD** | เปิดใช้งานบัญชี (บังคับ) และเข้าสู่ระบบแทนรหัสผ่านก็ได้ — OAuth 2.0 code flow จริง |
| **Email OTP** | ชั้นที่สองของการเข้าสู่ระบบด้วยรหัสผ่าน — 6 หลัก อายุ 10 นาที ขอใหม่ได้ทุก 60 วินาที |

ขั้นตอน:

1. เปิดลิงก์เชิญ → ระบบตรวจ token (ยังไม่หมดอายุ ยังไม่ถูกใช้)
2. หน้าสมัครแสดงอีเมลที่ถูกเชิญแบบอ่านอย่างเดียว (แก้ไม่ได้ กัน invite ถูกใช้ผิดคน)
3. กรอก คำนำหน้า / ชื่อ / นามสกุล / เบอร์โทร / รหัสผ่าน (ต้อง ≥ 8 ตัว มีตัวเลขและตัวอักษร)
4. กด "ถัดไป" → ระบบส่ง OTP ไปที่อีเมลนั้น
5. กรอก OTP 6 หลัก → ผ่านแล้วสร้าง `User` (`emailVerifiedAt` = now) และ mark invitation เป็น `ACCEPTED`
6. ล็อกอินอัตโนมัติ แล้วพาไปหน้าแรกตาม role

> **[สมมติฐาน]** ผิด OTP เกิน 5 ครั้ง → invalidate รหัสนั้น ต้องกดขอใหม่

## 3. Journey B — สร้างหน่วยงาน

### 3.0 ขั้นตอนการอนุมัติที่แสดงบนหน้าจอ

| ขั้น | ชื่อที่หน้าจอใช้ | `review_task.task_type` | บทบาทที่รับผิดชอบ |
| --- | --- | --- | --- |
| 1 | เจ้าหน้าที่ BDI ตรวจสอบเอกสาร | `BDI_OFFICER_REVIEW` | `BDI_OFFICER` |
| 2 | ผู้มีอำนาจของหน่วยงานลงนามเห็นชอบ | `ORGANIZATION_APPROVAL` | `ORGANIZATION_APPROVER` |
| 3 | BDI อนุมัติขั้นสุดท้าย | `BDI_FINAL_APPROVAL` | `BDI_FINAL_APPROVER` |

ตารางนี้ประกาศไว้เป็นข้อมูลที่ `backend/src/lib/journey-steps.ts` — ที่เดียวในระบบที่รู้ลำดับด่าน
ทั้งเส้น หน้าจอ (stepper บนหน้ารายละเอียด คอลัมน์ความคืบหน้าในตาราง การ์ดหน้าแรก) และบล็อก
ขั้นตอนท้ายอีเมล อ่านจากที่นั่นทั้งหมด **แก้ลำดับที่นี่ต้องแก้ที่ไฟล์นั้นและที่ตัว state machine
ใน `routes/organizations.ts` พร้อมกัน**

ระหว่างที่คำขออยู่ในสถานะ `RETURNED` จะ**ไม่มีขั้นไหนเป็นขั้นปัจจุบัน** — หน้าจอขึ้นแถบ
"ขณะนี้อยู่ที่หน่วยงาน — รอแก้ไขตามที่ผู้ตรวจส่งกลับ แล้วนำส่งใหม่" แทน เพราะ
`ORGANIZATION_REVISION` มีอยู่ใน enum แต่ไม่เคยถูกเปิดเป็น task จริง

### 3.1 State machine ของหน่วยงาน

สถานะทั้งสี่มาจาก Notion โดยตรง เพิ่ม `DRAFT` เข้ามาเพราะสเปกมีปุ่ม "บันทึกแบบร่าง"

```
        ┌─────────┐
        │  DRAFT  │  ผู้ใช้หน่วยงานกำลังกรอก (ยังไม่ส่ง)
        └────┬────┘
             │ นำส่งฟอร์มสร้างหน่วยงาน
             ▼
   ┌──────────────────────┐        ต้องปรับปรุง       ┌──────────────────┐
   │  PENDING_BDI_REVIEW  │ ───────────────────────▶ │  NEEDS_REVISION  │
   │  รอตรวจสอบจาก BDI    │ ◀─────────────────────── │  รอการแก้ไข       │
   └──────────┬───────────┘        แก้แล้วส่งใหม่      └──────────────────┘
              │ BDI Officer อนุมัติ
              ▼
   ┌────────────────────────────┐
   │  PENDING_SIGNATORY_REVIEW  │  รอตรวจสอบจากผู้มีอำนาจ
   └──────────┬─────────────────┘
              │ ผู้มีอำนาจกระทำการแทน เห็นชอบ
              ▼
   ┌──────────────────────────┐
   │  PENDING_BDI_APPROVAL    │  รอ BDI Approver ลงนาม
   └──────────┬───────────────┘
              │ BDI Approver เห็นชอบและลงนาม
              ▼
        ┌──────────┐
        │  ACTIVE  │  เปิดใช้งาน
        └──────────┘
```

ทุกครั้งที่สถานะเปลี่ยน บันทึกลง `OrganizationEvent` (ใคร ทำอะไร เมื่อไหร่ หมายเหตุอะไร)
เพื่อให้แสดง timeline ได้และตรวจสอบย้อนหลังได้

> **[สมมติฐาน]** `NEEDS_REVISION` จากผู้มีอำนาจหรือ BDI Approver ก็ส่งกลับมาที่ `NEEDS_REVISION` เหมือนกัน
> และเมื่อผู้ใช้แก้แล้วส่งใหม่ จะกลับไปเริ่มที่ `PENDING_BDI_REVIEW` เสมอ

### 3.2 ขั้นตอนที่ 1 — ผู้ใช้จากหน่วยงานกรอกข้อมูล

1. ผู้ใช้ role `ORG_USER` ที่ยังไม่มีหน่วยงาน ล็อกอินเข้ามา
2. หน้าแรกแสดง **empty state กลางจอ** พร้อมปุ่ม `สร้างหน่วยงาน` — เป็นเมนูเดียวที่เห็นและกดได้
   (เมนูอื่นซ่อนทั้งหมดตามสเปก)
3. ฟอร์มแบ่งสามส่วนตามภาพในสเปก:

**ส่วนที่ 1 — ข้อมูลหน่วยงาน**

| ฟิลด์ | ชนิด | การตรวจสอบ |
| --- | --- | --- |
| ชื่อหน่วยงาน | free text | บังคับ, 3–200 ตัวอักษร |
| ที่อยู่ (บ้านเลขที่/ถนน) | free text | บังคับ |
| จังหวัด | dropdown | บังคับ, 77 จังหวัด |
| อำเภอ/เขต | dropdown | บังคับ, กรองตามจังหวัด |
| ตำบล/แขวง | dropdown | บังคับ, กรองตามอำเภอ |
| รหัสไปรษณีย์ | text | บังคับ, 5 หลัก **[สมมติฐาน]** เติมอัตโนมัติจากตำบล |
| อีเมลหน่วยงาน | free text | บังคับ, ตรวจ format |

**ส่วนที่ 2 — ผู้มีอำนาจกระทำการแทน**

| ฟิลด์ | ชนิด | การตรวจสอบ |
| --- | --- | --- |
| คำนำหน้า | dropdown | บังคับ |
| ชื่อ-นามสกุล | free text | บังคับ |
| ตำแหน่ง | free text | บังคับ |
| อีเมล | free text | บังคับ, ตรวจ format — **อีเมลนี้จะถูกใช้เชิญเข้าระบบ** |
| เลขบัตรประชาชน | ตัวเลข 13 หลัก | บังคับ, ตรวจ checksum ตามมาตรฐานไทย |
| เบอร์โทรศัพท์ | free text | บังคับ, ตรวจรูปแบบเบอร์ไทย |
| คำสั่งแต่งตั้งผู้มีอำนาจกระทำการแทน | ไฟล์ pdf | **บังคับ**, ≤ 10 MB |
| คำสั่งมอบอำนาจ | ไฟล์ pdf | ไม่บังคับ, ≤ 10 MB |

**ส่วนที่ 3 — ผู้กรอกข้อมูล**

| ฟิลด์ | ชนิด | การตรวจสอบ |
| --- | --- | --- |
| คำนำหน้า | dropdown | บังคับ |
| ชื่อ-นามสกุล | free text | บังคับ |
| ตำแหน่ง | free text | บังคับ |
| ฝ่าย/กอง/สำนัก | free text | บังคับ |
| อีเมล | free text | บังคับ, ตรวจ format |
| เบอร์โทรศัพท์ | free text | บังคับ, ตรวจรูปแบบ |

> สเปกใน Notion ระบุ "ตำแหน่ง" ซ้ำสองครั้งในส่วนที่ 3 — ตีความว่าเป็นความซ้ำซ้อนในการเขียน
> จึงเก็บ **ตำแหน่ง** กับ **ฝ่าย/กอง/สำนัก** อย่างละหนึ่งช่อง **[สมมติฐาน]**

4. ปุ่ม `บันทึกแบบร่าง` — ตรวจข้อมูลเบื้องต้น ถ้าไม่ผ่านแสดง **toast เตือน** ตามสเปก
   และไฮไลต์ช่องที่ผิดพร้อมข้อความใต้ช่อง
5. เมื่อผ่านการตรวจ ระบบ **สร้าง PDF จาก template** โดยเติมข้อมูลที่กรอก แล้วแสดงให้ผู้ใช้ตรวจ
   (แสดงแบบฝัง preview เต็มหน้า พร้อมปุ่มดาวน์โหลด)
6. ผู้ใช้กด `นำส่งฟอร์มสร้างหน่วยงาน`
7. ระบบบันทึก, เปลี่ยนสถานะเป็น `PENDING_BDI_REVIEW`, ส่งอีเมลแจ้ง BDI Officer ทุกคน
8. redirect ไปหน้ารายละเอียดหน่วยงาน ซึ่งแสดงสถานะและ timeline

### 3.3 ขั้นตอนที่ 2 — BDI Officer ตรวจสอบ

1. เมนู **หน่วยงาน** แสดงตารางที่มีคอลัมน์ตามสเปก:
   ชื่อหน่วยงาน · ชื่อผู้สร้าง + อีเมลผู้สร้าง · สถานะ
   พร้อม **filter ได้ทุกคอลัมน์** และค้นหาข้อความ
2. เปิดดูรายละเอียด → เห็นข้อมูลทุกส่วน, ไฟล์แนบ, และ **PDF ที่ generate** แบบฝังในหน้า
3. ปุ่ม `ต้องปรับปรุง` → เปิด **modal** ให้พิมพ์รายละเอียดสิ่งที่ต้องแก้ → ยืนยัน
   → สถานะเป็น `NEEDS_REVISION` + ส่งอีเมลแจ้งเจ้าหน้าที่หน่วยงาน (แนบข้อความที่พิมพ์)
4. ปุ่ม `อนุมัติ` →
   - ถ้าอีเมลผู้มีอำนาจกระทำการแทน **ยังไม่มีในระบบ** → สร้าง invitation role `ORGANIZATION_APPROVER`
     ผูกกับหน่วยงานนี้ แล้วส่งลิงก์สมัคร (เข้าสู่ Journey A)
   - ถ้ามีแล้ว → ผูก role `ORG_APPROVER` ของหน่วยงานนี้ให้ทันที
   - สถานะ → `PENDING_SIGNATORY_REVIEW`, ส่งอีเมลพร้อมรายละเอียดคำขอ

### 3.4 ขั้นตอนที่ 3 — ผู้มีอำนาจกระทำการแทน

1. ล็อกอิน (หรือสมัครผ่านลิงก์ที่ได้รับ) → เห็นรายการที่รอตนเองพิจารณา
2. เปิดดู → รีวิว PDF
3. กด `เห็นชอบ` → สถานะ `PENDING_BDI_APPROVAL` + แจ้ง BDI Approver
   หรือกด `ต้องปรับปรุง` → `NEEDS_REVISION` + แจ้งผู้กรอก

### 3.5 ขั้นตอนที่ 4 — BDI Approver

1. เห็นรายการสถานะ `PENDING_BDI_APPROVAL`
2. รีวิว PDF แล้วกด `เห็นชอบและลงนาม` → สถานะ `ACTIVE`
3. ระบบแจ้งทุกฝ่ายว่าหน่วยงานเปิดใช้งานแล้ว และปลดล็อกเมนูอื่นให้ผู้ใช้ของหน่วยงานนั้น

## 4. Journey C — ขอลงทะเบียนชุดข้อมูล (Dataset Registration)

ที่มา: Notion → *Dataset Registration by Organization User*

หน่วยงานที่เปิดใช้งานแล้วยื่นคำขอ **ลงทะเบียนชุดข้อมูล** ทีละชุด คำขอผ่านการตรวจสามด่าน
(1. BDI Officer → 2. Organization Approver → 3. BDI Approver)

> **แก้ไข 2026-08-30** — สเปกเดิมมี *Final Check* ของ BDI Officer คั่นระหว่างด่าน 2 กับ 3
> (ข้อ 3.2) ด่านนั้น **ถูกยกเลิกทั้งหมด** ตามการ์ด *แก้ flow dataset registration
> (เอา BDI ตรวจซ้ำออก)* — เมื่อผู้มีอำนาจของหน่วยงานลงนามแล้ว คำขอไปที่ BDI Approver ทันที
> เลขขั้นบนหน้าจอจึงตรงกับเลขด่านของสเปกพอดี ไม่ต้องแปลงอีกต่อไป

### 4.0 ขั้นตอนการอนุมัติที่แสดงบนหน้าจอ

| ขั้น | ชื่อที่หน้าจอใช้ | `review_task.task_type` | บทบาทที่รับผิดชอบ |
| --- | --- | --- | --- |
| 1 | เจ้าหน้าที่ BDI ตรวจสอบเอกสาร | `BDI_OFFICER_REVIEW` | `BDI_OFFICER` |
| – | ผู้เชี่ยวชาญด้านข้อมูลพิจารณา — **ไม่บังคับ** | `DATASET_SPECIALIST_REVIEW` | `BDI_DATASET_SPECIALIST` |
| 2 | ผู้มีอำนาจของหน่วยงานลงนามเห็นชอบ | `ORGANIZATION_APPROVAL` | `ORGANIZATION_APPROVER` |
| 3 | BDI อนุมัติขั้นสุดท้าย | `BDI_FINAL_APPROVAL` | `BDI_FINAL_APPROVER` |

**หนึ่ง `task_type` คือหนึ่งขั้น** เส้นทางนี้จึงมีรูปเดียวกับเส้นทาง B ทุกประการ ต่างกันแค่
ทางแยกผู้เชี่ยวชาญ

ขั้นผู้เชี่ยวชาญ **ไม่ถูกนับใน "จาก 3"** และไม่มีเลขกำกับ — มันเป็นทางแยกที่เจ้าหน้าที่เลือกเปิด
ไม่ใช่ด่านที่ทุกคำขอต้องผ่าน ถ้านับรวม จำนวนขั้นจะเปลี่ยนกลางคันเมื่อมีการมอบหมาย ซึ่งอ่านแล้ว
เหมือนระบบเปลี่ยนกติกา แต่ยังแสดงในรายการเสมอ เพื่อบอกความจริงว่าทางแยกนี้มีอยู่

**คำขอที่ถูกส่งกลับ *หลัง* หน่วยงานลงนามไปแล้ว เมื่อนำส่งใหม่จะกลับไปที่ขั้นที่ 1 และต้อง
เดินผ่านการลงนามอีกครั้ง** ไม่มีทางลัดข้ามการลงนาม เพราะลายมือชื่อที่มีอยู่อยู่บนเนื้อหาที่
ไม่ใช่ฉบับนี้แล้ว กติกานี้อยู่ใน `nextStageAfter()` ของ `routes/dataset-requests.ts` และใน
`lib/journey-steps.ts` — ต้องแก้พร้อมกันเสมอ

### 4.1 เงื่อนไขก่อนเริ่ม (pre-requisite)

ปุ่ม `ลงทะเบียนชุดข้อมูล` จะกดได้ก็ต่อเมื่อครบทั้งสามข้อ ถ้าไม่ครบให้ปุ่ม disabled
พร้อมข้อความบอกว่ายังขาดอะไร (ไม่ซ่อนปุ่ม — ผู้ใช้ต้องรู้ว่าต้องทำอะไรต่อ)

1. ผู้ใช้ล็อกอินอยู่ และมี role `ORG_USER`
2. หน่วยงานของผู้ใช้อยู่ในสถานะ `ACTIVE` (ผ่าน Journey B ครบแล้ว)
3. หน่วยงานมีบัญชีที่ `ACTIVE` แล้วทั้ง `ORG_USER` และ `ORG_APPROVER`

> **[สมมติฐาน]** ข้อ 3 ตรวจจากผู้ใช้ที่ `organizationId` ตรงกับหน่วยงานนี้ **หรือ** อีเมลตรงกับ
> `signatoryEmail` ของหน่วยงาน — เพราะผู้มีอำนาจที่มีบัญชีอยู่ก่อนแล้วจะถูกผูก role ให้
> แต่ยังไม่ถูกย้าย `organizationId` ใน Journey B

### 4.2 State machine ของคำขอลงทะเบียนชุดข้อมูล

- `NEEDS_REVISION` แก้แล้วส่งใหม่ **กลับไปเริ่มที่ `PENDING_OFFICER_REVIEW` เสมอ**

  ซึ่งจะต้องลงนามใหม่ ยืนยันเมื่อ 2026-08-30 ตอนยกเลิกด่านตรวจซ้ำ
- `APPROVED` และ `REJECTED` เป็นสถานะปลายทาง แก้ไขหรือย้อนกลับไม่ได้
- ทุกการเปลี่ยนสถานะบันทึกลง `DatasetRequestEvent` (ใคร จากสถานะไหน ไปสถานะไหน หมายเหตุอะไร)
  หน้า timeline และ audit อ่านจากตารางนี้ — ห้ามแก้ `status` โดยไม่บันทึก event

### 4.3 ขั้นตอนที่ 1 — Org User กรอกและนำส่ง

Org User **เห็นและจัดการคำขอทุกรายการในหน่วยงานของตัวเอง** ไม่จำเป็นต้องเป็นคนสร้าง (สเปกข้อ 1)

1. กด `ลงทะเบียนชุดข้อมูล` → ระบบสร้างคำขอสถานะ `DRAFT` พร้อม **เลขที่คำขอ** `DR-<ปี ค.ศ.>-<ลำดับ 4 หลัก>`
2. กรอกข้อมูลสี่ส่วน (ดูตารางด้านล่าง)
3. `บันทึกแบบร่าง` ได้ตลอด — ตอนบันทึกร่างไม่บังคับความครบถ้วน
4. กด `ตรวจสอบและสร้าง PDF` → ระบบ validate ทั้งฉบับ
   - **ไม่ผ่าน** → toast เตือน + ไฮไลต์ช่องที่ผิด + เลื่อนจอไปช่องแรกที่ผิด
   - **ผ่าน** → สร้าง PDF A4 จากข้อมูลที่กรอก แล้วพาไปหน้า Preview
5. หน้า Preview แสดง PDF และรายการไฟล์แนบทั้งหมด → กด `นำส่งคำขอ`
6. สถานะเป็น `PENDING_OFFICER_REVIEW`, ส่งอีเมล + in-app notification ให้ BDI Officer ทุกคน
   และ**ล็อกการแก้ไข** จนกว่าจะถูกส่งกลับ

**ส่วนที่ 1 — Metadata ของชุดข้อมูล**

| ฟิลด์ | ชนิด | การตรวจสอบ |

### 4.4 ขั้นตอนที่ 2 — BDI Officer Pre-review และ Data Specialist

BDI Officer **ทุกคนเห็นคำขอทั้งหมดในระบบ** (สเปกข้อ 2)

1. เปิดคำขอ → เห็นข้อมูลครบทุกส่วน ไฟล์แนบ และ PDF ที่ระบบสร้าง
2. **ข้อมูลไม่เพียงพอ** → `ต้องปรับปรุง` + ระบุรายการที่ต้องแก้ (≥ 10 ตัวอักษร)
   → `NEEDS_REVISION` + อีเมล + in-app notification ถึง Org User
3. **ข้อมูลเพียงพอ** → เลือกทำอย่างใดอย่างหนึ่งหรือทั้งสอง
   - **Assign Data Specialist (ไม่บังคับ)** — เลือกจากบัญชี `BDI_DATASET_SPECIALIST` ที่มีอยู่แล้วในระบบ
     กด assign แล้วคำขอจะขึ้นในหน้ารายการของผู้เชี่ยวชาญคนนั้น
     พร้อมส่งอีเมล + notification ให้ผู้เชี่ยวชาญ (ถอน assign ได้)
   - **ส่งต่อ** — `PENDING_ORG_APPROVER` + แจ้งผู้มีอำนาจของหน่วยงาน
4. **Data Specialist** ที่ถูก assign ทำได้สองอย่าง
   - บันทึก **Review Comment** ไว้ใน timeline โดยไม่เปลี่ยนสถานะ (ประสานงานนอกรอบตามสเปก)
   - `ต้องปรับปรุง` — ส่งกลับ `NEEDS_REVISION` เองได้ (หรือให้ BDI Officer เป็นคนกดแทน)
   - กรณีไม่ต้องแก้ ผู้เชี่ยวชาญแจ้ง BDI Officer นอกระบบ แล้ว Officer เป็นคนกดส่งต่อ
     — ระบบไม่บังคับว่าต้องมีความเห็นของผู้เชี่ยวชาญก่อนส่งต่อ

> **[สมมติฐาน]** `[Next Phase]` ในสเปก (สร้าง/เชื่อม Jira ticket อัตโนมัติเมื่อ assign)
> ยังไม่ทำในเฟสนี้ เก็บ `assignedSpecialistId` และเวลาที่ assign ไว้ให้เชื่อมภายหลังได้

### 4.5 ขั้นตอนที่ 3 — Organization Approver

Org Approver **เห็นคำขอทุกรายการในหน่วยงานของตัวเอง** (สเปกข้อ 3)

1. เปิดคำขอ → รีวิว PDF และเอกสารแนบ
2. `ต้องปรับปรุง` + ระบุเหตุผล → `NEEDS_REVISION` + แจ้ง Org User
3. `เห็นชอบและลงนาม` → บันทึกการลงนาม (ผู้ลงนาม + เวลา) → `PENDING_BDI_APPROVAL`
   + แจ้ง **BDI Approver ทุกคน** ด้วยอีเมลที่บอกชื่อผู้ลงนาม

> **ยกเลิกแล้ว 2026-08-30** — สเปกข้อ 3.2 เคยให้ BDI Officer ตรวจซ้ำอีกรอบหลังการลงนาม
> ก่อนส่งให้ BDI Approver ด่านนั้นถูกเอาออกทั้งหมดตามการ์ด *แก้ flow dataset registration*
> เจ้าหน้าที่ BDI จึงไม่ได้รับแจ้งเมื่อหน่วยงานลงนามอีกต่อไป และไม่มีอะไรให้ทำหลังจากนั้น

> **[สมมติฐาน]** "การลงนาม" ของ Org Approver เป็นการ **stamp ว่ากดยอมรับแล้ว** (ผู้ลงนาม + เวลา
> บันทึกลง event และพิมพ์ลงท้าย PDF) ไม่ใช่ digital signature จริง — ตรงกับที่สเปกเขียนไว้ใน
> *To be confirm requirements*

### 4.6 ขั้นตอนที่ 4 — BDI Approver (Final Approval)

1. `ต้องปรับปรุง` + ระบุรายการที่ต้องแก้ → `NEEDS_REVISION` + แจ้ง Org User
2. `ไม่อนุมัติ` + ระบุเหตุผล → `REJECTED` + แจ้ง stakeholders ทุกคน + **ปิดกระบวนการ**
3. `อนุมัติ` → `APPROVED`
   - ระบบ **สร้าง PDF ฉบับสมบูรณ์ใหม่** ที่มีเลขที่คำขอ ผู้ลงนามทุกด่าน และวันที่อนุมัติ
     ให้ดาวน์โหลดได้ (A4)
   - แจ้ง stakeholders ทุกคน
   - จบกระบวนการด้วยความสำเร็จ (`END_SUCCESS`)

> **[สมมติฐาน]** *stakeholders* = ผู้สร้างคำขอ · ผู้ใช้ทุกคนในหน่วยงานนั้น · ผู้มีอำนาจของหน่วยงาน ·
> BDI Officer ทุกคน · Data Specialist ที่ถูก assign · BDI Approver ทุกคน
> (สเปกตั้งคำถามนี้ไว้เองใน *To be confirm requirements*)

### 4.7 สิทธิ์การมองเห็น

| ใคร | เห็นคำขอไหน |
| --- | --- |
| `ORG_USER` | ทุกคำขอของหน่วยงานตนเอง (จัดการได้แม้ไม่ได้เป็นคนสร้าง) |
| `ORG_APPROVER` | ทุกคำขอของหน่วยงานตนเอง |
| `BDI_OFFICER` | ทุกคำขอในระบบ |
| `BDI_FINAL_APPROVER` | ทุกคำขอในระบบ **[สมมติฐาน]** (สเปกระบุชัดเฉพาะ Officer) |
| `BDI_DATASET_SPECIALIST` | เฉพาะคำขอที่ถูก assign ให้ตนเอง |

### 4.8 การแจ้งเตือนในระบบ (in-app notification)

- **ไม่ต้อง real time** ตามสเปก — หน้าเว็บ fetch ตอนโหลดหน้าใหม่หรือเปลี่ยนหน้าก็พอ
- กระดิ่งบน header แสดงจำนวนที่ยังไม่อ่าน กดแล้วเห็นรายการล่าสุด 20 รายการ
  แต่ละรายการลิงก์ไปที่คำขอนั้น และกด "อ่านแล้ว" ได้ทั้งรายการเดียวและทั้งหมด
- ทุกครั้งที่ส่งอีเมลของเส้นทาง C ระบบสร้าง notification คู่กันเสมอ
- เมื่อคำขอถูกส่งกลับให้แก้ หน้ารายละเอียด **ต้องแสดงว่าแก้เรื่องอะไร โดยใคร เมื่อไหร่**
  (อ่านจาก event ล่าสุดที่เป็นการส่งกลับ ไม่ใช่แค่ข้อความล้วน)

### 4.9 Activity / Audit log

เก็บลง PostgreSQL ตาราง `ActivityLog` แยกจาก timeline ที่ผู้ใช้เห็น เพราะเก็บละเอียดกว่าและไม่แสดงบนจอ

| ฟิลด์ | เก็บอะไร |
| --- | --- |
| `createdAt` | เวลาแบบ UTC (ISO 8601) |
| `actorId` · `actorName` · `actorRoles` · `actorOrganizationId` | ข้อมูลผู้กระทำ ณ เวลานั้น |
| `targetType` · `targetId` · `targetRef` | ประเภท/ID ของเป้าหมาย และเลขที่คำขอ |
| `action` | `CREATE` · `UPDATE` · `SUBMIT` · `REVIEW` · `APPROVE` · `REJECT` · `RETURN_FOR_REVISION` · `ASSIGN` · `DELETE` · `DOWNLOAD` |
| `before` · `after` | JSON เฉพาะฟิลด์ที่เปลี่ยน (ก่อน/หลัง) |
| `ipAddress` | IP ของผู้ใช้ขณะทำรายการ |

> ชื่อและ role ของผู้กระทำถูก **คัดลอกลงในแถว** ไม่ใช่อ้างอิงอย่างเดียว เพื่อให้ log ยังอ่านได้
> ถูกต้องแม้ผู้ใช้จะเปลี่ยนชื่อหรือถูกลบภายหลัง

## 6. คำถามที่ยังค้าง — ต้องยืนยันกับเจ้าของสเปก

Notion เขียนคำถามเหล่านี้ไว้เอง และผมเพิ่มที่พบระหว่างออกแบบ

1. **ชื่อหน่วยงาน** — Notion ตั้งคำถามว่าควรมีรายการหน่วยงานให้เลือกพร้อมที่อยู่หรือไม่
   ตอนนี้ทำเป็น free text ตามสเปกหลัก แต่โครงสร้าง `Organization.name` รองรับการเปลี่ยนเป็น
   reference ไปยังทะเบียนหน่วยงานภายหลังได้
2. **ผู้ใช้หลายคนต่อหน่วยงาน** — ออกแบบให้ได้ไว้ก่อน (ดูข้อ 1)
3. **ขั้นตอนที่ 2 ข้อ 5 ในสเปกเขียนค้างไว้** ("เมื่อผู้มีอำนาจกระทำการแทน") — ตีความตามข้อ 3.4
4. **การลงนามของ BDI Approver** — สเปกเขียนว่า "ลงนาม" ยังไม่ระบุว่าเป็น digital signature จริง
   หรือแค่กดยืนยัน ตอนนี้ทำเป็นกดยืนยันพร้อมบันทึกผู้ลงนามและเวลาลง audit log

   ให้ตรงกับโครงสร้างข้อมูลและ CI

### เพิ่มจาก Journey C

7. **ฟิลด์ของ Metadata / Delivery Method / Legal Conditions** — สเปกระบุแค่ชื่อสามกลุ่ม
   ไม่ได้ลงรายละเอียดว่ามีฟิลด์อะไรบ้าง ตาราง §4.3 ทั้งหมดจึงเป็น **[สมมติฐาน]**
   อ้างอิงแนวทาง metadata ของข้อมูลเปิดภาครัฐ — ต้องให้เจ้าของสเปกยืนยันหรือแทนที่ทั้งชุด
8. **Stakeholders คือใคร** — สเปกตั้งคำถามนี้ไว้เอง ตอนนี้ตีความตาม §4.6
9. **การ sync กับ DII หลังอนุมัติ** — ที่คุยไว้คือมี API endpoint เดียวให้ DII ยิงเข้ามา
   ยังไม่ได้ทำในเฟสนี้ เพราะยังไม่มีสเปกของ payload และวิธียืนยันตัวตนของ DII
10. **Jira integration** — สเปกทำเครื่องหมาย `[Next Phase]` ไว้ และ flow error handling
    ยังไม่ได้ข้อสรุป จึงเก็บแค่ข้อมูลการ assign ไว้ก่อน
11. **ER-Diagram ใน Notion ต่างจากสคีมาที่ใช้จริง** — ไดอะแกรมวางไว้เป็นภาพรวมของเฟสถัดไป
    (`ROLE` / `USER_ROLE_ASSIGNMENT` แยกตาราง, `ATTACHMENT` แบบ polymorphic,
    `REVIEW_TASK`, `SIGNATURE_CONFIRMATION`, `LEGAL_ACCEPTANCE`)
    ส่วนโค้ดปัจจุบันเก็บ role เป็น array บน `User` และมี attachment แยกตามเจ้าของ
    เฟสนี้จึงทำตามโครงเดิมของ Journey A/B เพื่อไม่ต้องรื้อของที่ใช้งานอยู่ —
    แต่คงชื่อฟิลด์ที่ไดอะแกรมกำหนดไว้ (`request_number`, การลงนาม, การยอมรับเงื่อนไข)
    ให้ย้ายไปโครงใหม่ได้โดยไม่เสียข้อมูล
