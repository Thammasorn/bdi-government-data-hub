# 17 · การสร้างเอกสารกฎหมายจาก template

การ์ด Notion: **Organization Registration PDF legal doc render**

เอกสารข้อตกลง A0–A3 ของเส้นทาง B ไม่ได้ถูกวาดขึ้นด้วยโค้ด แต่มาจากไฟล์ `.docx` ที่ฝ่ายกฎหมาย
BDI เป็นเจ้าของ ระบบเติมข้อมูลของคำขอลงใน placeholder แล้วให้ LibreOffice จัดหน้าเป็น PDF

## 1 · ทำไมต้องเดินทางนี้

โจทย์มีสองข้อที่ต้องเป็นจริงพร้อมกัน:

1. **ผู้ใช้ต้องแก้เอกสารได้เองโดยไม่ต้องแก้โค้ด** — ถ้อยคำในข้อตกลงเป็นของฝ่ายกฎหมาย
   การแก้หนึ่งบรรทัดไม่ควรกลายเป็นงาน deploy
2. **เลย์เอาต์ต้องไม่เปลี่ยน** — ฟอนต์ ระยะ ย่อหน้า และการตัดบรรทัดต้องเป็นของ template

สามทางที่พิจารณา:

| ทาง | แก้เอกสารเองได้ | เลย์เอาต์ตรง template | ค่าที่เติมไหลไปกับข้อความ |
|---|---|---|---|
| **.docx → LibreOffice → PDF** (เลือกทางนี้) | ได้ | ได้ (LibreOffice จัดหน้าจากไฟล์ต้นฉบับ) | ได้ |
| วาดข้อความทับ PDF ตามพิกัด (pdf-lib) | **ไม่ได้** — อัปโหลด template ใหม่แล้วพิกัดผิดทั้งหมด | ได้ | **ไม่ได้** — ชื่อหน่วยงานยาวกว่าช่องว่างจะล้น |
| เรียงพิมพ์ใหม่ด้วย PDFKit (แบบ `lib/pdf.ts`) | **ไม่ได้** — ถ้อยคำอยู่ใน TypeScript | ใกล้เคียง แต่ไม่ใช่ของ template | ได้ |

ข้อ 2 ของทางกลางเป็นตัวตัดสิน: ช่องว่างใน A0 อยู่กลางย่อหน้าที่จัดชิดขอบสองข้าง
(`ตั้งอยู่เลขที่ ___ ถนน ___ แขวง/ตำบล ___`) ค่าที่เติมต้องดันบรรทัดถัดไปเอง ซึ่งการวาดทับ
ตามพิกัดทำไม่ได้

## 2 · ตัวแปลงคือ gotenberg ไม่ใช่ soffice ที่เรียกตรง

`gotenberg/` เป็นบริการหนึ่งใน compose ต่อยอดจาก image `gotenberg/gotenberg:8-libreoffice`
(ตัด Chromium ออกเพราะระบบนี้ไม่แปลง HTML) เรียกผ่าน `POST /forms/libreoffice/convert`

เรียก `soffice` ตรงจาก backend ก็ทำได้ แต่ต้องจัดการ user profile ที่ชนกันเมื่อมีหลาย request
พร้อมกัน กับ process ที่ค้าง — gotenberg ทำสองอย่างนั้นให้อยู่แล้ว และเป็นวิธีที่ใช้กันจริงบน
production สำหรับงานแปลงเอกสารด้วย LibreOffice

**ฟอนต์ TH SarabunPSK ถูกฝังไว้ใน image ของ gotenberg** ไม่ใช่แค่ในไฟล์ `.docx`
LibreOffice คำนวณการตัดบรรทัดและการแบ่งหน้าจากฟอนต์ที่ติดตั้งในเครื่อง ถ้าไม่มีมันจะแทนด้วย
ฟอนต์อื่นแล้วเลย์เอาต์เลื่อนทั้งฉบับ — อาการจะดูเหมือน template พัง ทั้งที่ template ถูก
`gotenberg/Dockerfile` จึงตรวจด้วย `fc-list | grep "TH SarabunPSK"` ตอน build และ build ล้ม
ถ้าไม่เจอ

ถ้าบริการนี้ไม่ขึ้น การสร้างเอกสารตอบ 503 พร้อมเหตุผล **ไม่มี fallback โดยตั้งใจ** —
ปล่อย PDF ที่เลย์เอาต์เพี้ยนออกไปให้หน่วยงานลงนามแย่กว่าบอกตรง ๆ ว่าตัวแปลงยังไม่พร้อม

### ต่างจาก PDF ที่ Word สร้าง

ไฟล์อ้างอิงใน `assets/document-template/*.pdf` ถูกแปลงด้วย **MS Word บน macOS** เทียบกับ
ผลของ LibreOffice ทีละหน้าแล้ว ฟอนต์ ถ้อยคำ การตัดบรรทัดในย่อหน้า เส้นประ และตำแหน่งช่อง
ลงนามทั้งสองฝ่ายตรงกัน ต่างสองอย่าง:

- LibreOffice ไม่ทำตาม `w:pgNumType w:fmt="thaiNumbers"` เลขหน้าจึงเป็น `2` ไม่ใช่ `๒`
- ระยะบรรทัดของ TH SarabunPSK แน่นกว่าของ Word เล็กน้อย A0 จึงจบใน 2 หน้าแทน 3 —
  หน้าที่ 3 ของฉบับ Word เป็น**หน้าเปล่า** ที่เกิดจากย่อหน้าว่างท้ายเอกสาร

ทั้งสองข้อเป็นข้อจำกัดของ LibreOffice ไม่ใช่ของ template และเนื้อหาไม่ได้หายไป

## 3 · template อยู่ในฐานข้อมูล ไม่ได้อยู่ใน repo

```
legal.legal_document            A0–A4 (seed:masters สร้างให้)
  └─ legal_document_version     หนึ่งแถวต่อหนึ่งเวอร์ชันของไฟล์
       ├─ attachment (LEGAL_DOCUMENT)  .docx ต้นแบบ  ← ของจริงที่เอาไปเติมค่า
       └─ attachment (GENERATED_FORM)  PDF ที่ render ไว้ตอน publish ให้เปิดอ่าน
```

ไฟล์ใน `backend/src/assets/legal-templates/` เป็น **ฉบับตั้งต้น** เท่านั้น `seed:masters` ใช้
สร้างเวอร์ชัน 1 หลังจากนั้นของจริงคือเวอร์ชันล่าสุดในฐานข้อมูล

สองไฟล์ต่อเวอร์ชันอยู่ต่าง `attachment_type` กัน เพราะ partial unique index ยอมให้มี `ACTIVE`
ได้แถวเดียวต่อ `(owner_type, owner_id, attachment_type)` การแปลงเป็น PDF ทำตอน publish
ครั้งเดียว ไม่ใช่ทุกครั้งที่มีคนเปิดดู — ผนวก A1–A3 ไม่มีช่องให้เติม ผลลัพธ์จึงเหมือนกันทุกครั้ง

### เปลี่ยน template

```bash
curl -X POST http://localhost:4330/api/admin/legal-documents/A0/versions \
  -H "x-admin-token: $ADMIN_API_TOKEN" \
  -F "file=@A0.docx;type=application/vnd.openxmlformats-officedocument.wordprocessingml.document"
```

ตอบ 201 พร้อมรายชื่อ placeholder ที่อ่านเจอ — ให้คนอัปโหลดยืนยันได้ว่าช่องที่ตั้งใจใส่ถูกอ่าน
ครบ เวอร์ชันเดิมกลายเป็น `SUPERSEDED` และคำขอที่ลงนามไว้แล้วยังชี้เวอร์ชันเดิมของมันอยู่

`GET /api/admin/legal-documents` คืนรายการเอกสาร ทุกเวอร์ชัน และ**รายชื่อตัวแปรทั้งหมดที่ใช้ได้**

ตรวจสองอย่างก่อนรับ ทั้งคู่ตอบ 400 พร้อมบอกว่าต้องแก้อะไร และ**ไม่เขียนอะไรลงฐานข้อมูลเลย**
ถ้าไม่ผ่าน:

1. ชื่อ placeholder ทุกตัวต้องอยู่ใน `TEMPLATE_VARIABLES` (`lib/document-render.ts`)
2. LibreOffice ต้องแปลงไฟล์นั้นเป็น PDF ได้จริง

ปล่อยไฟล์ที่ไม่ผ่านสองข้อนี้เข้าไปจะไปพังตอนหน่วยงานกดสร้างเอกสาร ซึ่งเป็นคนละคน คนละวัน
และเขาแก้อะไรไม่ได้เลย

## 4 · placeholder

`{{ }}` ไม่ใช่ `{ }` เพราะวงเล็บเดี่ยวชนกับข้อความในเอกสารกฎหมายเอง ตัวแทนค่าถูกแทนด้วย
`docxtemplater` (MIT) ซึ่งรวม run ที่ Word ผ่าไว้ก่อนจับคู่ — จำเป็น เพราะ Word ผ่า
`{{org.name}}` เป็นสามชิ้นได้ตามใจ (rsid, spell-check, language hint)

**เส้นแบ่งของ "แก้ได้โดยไม่ต้องแก้โค้ด"**: ผู้ดูแลเอกสารย้าย ลบ หรือใช้ placeholder ตัวไหน
ซ้ำกี่ที่ก็ได้ แต่การ**เพิ่มชื่อใหม่**ต้องมีคนต่อค่าให้มันในโค้ดก่อน (`lib/legal-values.ts`)

ตัวแปรทั้งหมดอยู่ใน `TEMPLATE_VARIABLES` — เรียกดูได้จาก `GET /api/admin/legal-documents`
ค่าวันที่และตัวเลขเป็นเลขไทยและปี พ.ศ. ตามที่ template เองตั้ง `thaiNumbers` ไว้

ค่าที่ยังไม่เกิดขึ้น (ลายมือชื่อที่ยังไม่มีใครลงนาม) เป็น**ค่าว่าง** ไม่ใช่ `-` หรือเส้นประ —
ช่องลายมือชื่อที่ว่างคือสิ่งที่บอกว่ายังไม่มีการลงนาม

`docs/tools/add-legal-placeholders.py` คือสคริปต์ที่ใส่ placeholder ลงในไฟล์ต้นฉบับครั้งแรก
เก็บไว้เป็นบันทึกว่าแก้อะไรจากของเดิมบ้าง **ไม่ต้องรันอีก** — ของจริงหลังจากนี้คือไฟล์ในฐานข้อมูล

สคริปต์นั้นลบมาร์ก TODO ที่ผู้ร่างทำไว้ที่ช่อง `ระบบ.....` ของ A0 ออกด้วย — **ไฮไลต์เหลืองและ
ตัวอักษรสีแดง** ทั้งคู่เป็นมาร์กของคนร่าง ไม่ใช่รูปแบบที่ต้องการ ถ้าปล่อยไว้ ข้อตกลงฉบับจริงจะมีแถบ
ไฮไลต์และตัวหนังสือสีแดงคาดผ่านชื่อระบบตัวเอง แตะเฉพาะ A0 และมีแค่สองจุดนั้น

### ผนวก A1–A3 ยังมีร่องรอยการร่างติดมาด้วย และตั้งใจไม่แตะ

นับจากไฟล์ที่ได้รับมา:

| เอกสาร | ไฮไลต์ | ขีดฆ่า | ตัวอักษรสีแดง |
|---|---|---|---|
| A1 (DPA) | 42 | 223 | 96 |
| A2 (PDPA) | 33 | 13 | 35 |
| A3 (NDA) | 139 | 155 | 24 |

ไฟล์ที่ระบบใช้เหมือนต้นฉบับทุกไบต์ มาร์กเหล่านี้จึงปรากฏใน PDF ที่หน่วยงานลงนามด้วย
**เป็นเรื่องเนื้อหาที่ฝ่ายกฎหมายต้องเคลียร์ ไม่ใช่เรื่องโค้ด** — ลบให้เองเท่ากับทีมพัฒนาไปตัดสินแทน
ว่าข้อความที่ขีดฆ่าไว้ควรอยู่หรือควรไป เมื่อได้ฉบับสะอาดมาแล้ว อัปโหลดทับเป็นเวอร์ชันใหม่ได้เลย
ไม่ต้องแก้โค้ด

## 5 · เอกสารทุกฉบับที่มี placeholder ถูกสร้างต่อคำขอ

**ไม่ใช่แค่ A0** ฉบับไหนมี `{{...}}` ฉบับนั้นจะถูก render ด้วยข้อมูลของคำขอและเก็บเป็นไฟล์ของ
คำขอนั้น ฉบับที่ไม่มี placeholder ใช้ไฟล์กลางของเวอร์ชันร่วมกันทุกหน่วยงาน เพราะผลลัพธ์
เหมือนกันหมด ไม่มีเหตุให้ทำสำเนา

`hasPlaceholders` ใน `publishedDocuments()` เป็นตัวตัดสิน — อ่านจากไฟล์ `.docx` จริง ไม่ได้
ดูจากรหัสเอกสาร เพิ่ม placeholder ลง A1 แล้วอัปโหลด ฉบับนั้นจะเริ่ม render ต่อคำขอทันที
โดยไม่ต้องแก้โค้ด และเอาออกก็กลับไปใช้ไฟล์กลางเอง

### เก็บหลายฉบับต่อคำขอได้อย่างไร

`uq_active_attachment_per_slot` เดิมยอมให้มี ACTIVE ได้แถวเดียวต่อ
`(owner_type, owner_id, attachment_type)` คำขอจึงเก็บ `GENERATED_FORM` ได้ฉบับเดียว —
เป็นเหตุผลที่ตอนแรกมีแค่ A0 ที่ถูก render

migration `20260819170000_attachment_per_legal_document` เพิ่มคอลัมน์
`attachment.legal_document_version_id` แล้วใส่เข้าไปใน index นั้น กลายเป็นหนึ่งฉบับ ACTIVE
ต่อหนึ่งเวอร์ชันเอกสาร **ไม่ต้องเพิ่มค่า enum ต่อรหัสเอกสาร** — A5 ในอนาคตใช้ได้เลย

index ใช้ `COALESCE(legal_document_version_id, '000…0')` ไม่ใช่คอลัมน์เปล่า ๆ เพราะ Postgres
นับ NULL ว่าไม่ซ้ำกัน ถ้าใส่ตรง ๆ ไฟล์ที่ผู้ใช้อัปโหลด (คำสั่งแต่งตั้ง หนังสือมอบอำนาจ ซึ่ง
คอลัมน์นี้เป็น NULL) จะมี ACTIVE ได้หลายแถวต่อ slot ทันที เป็นการคลายกฎที่ sheet `attachment`
กำหนดไว้โดยไม่ได้ตั้งใจ

A0 ที่สร้างไว้ก่อน migration มีคอลัมน์นี้เป็น NULL ระบบยอมรับไฟล์เดิมต่อไปและไม่ render ใหม่
ให้ — ไม่งั้นเอกสารที่อนุมัติแล้วจะเปลี่ยนบรรทัด "พิมพ์จากระบบโดย/วันที่" ทั้งที่เนื้อหาอื่นเท่าเดิม

### PDF กลางของฉบับที่มี placeholder เป็น "ฉบับเปล่า"

ตอน publish ถ้าเอกสารมี placeholder ระบบเติมค่าว่างก่อนแปลงเป็น PDF กลาง ไม่ได้แปลงตรง ๆ
ไม่งั้นไฟล์กลางจะมีข้อความ `{{org.name}}` โผล่ให้เห็นจริง ๆ

## 5.1 · A0 ถูกสร้างสามครั้งต่อคำขอ

`lib/organization-agreement.ts` มีทางเดินเดียว ต่างกันแค่ตอนนั้นมีลายมือชื่อของใครแล้ว:

| เมื่อ | ลายมือชื่อในเอกสาร |
|---|---|
| ผู้กรอกกด "ตรวจสอบและสร้าง PDF" | ยังไม่มีทั้งสองฝ่าย |
| ผู้มีอำนาจกระทำการแทนลงนาม | ฝ่ายหน่วยงาน |
| ผู้อนุมัติ BDI ลงนาม | ทั้งสองฝ่าย + ตราเห็นชอบ |

แต่ละครั้งเขียนทับ slot `GENERATED_FORM` ของคำขอ ฉบับก่อนหน้ากลายเป็น `REPLACED` ไม่ได้ถูกลบ
จึงยังตรวจย้อนได้ว่าผู้ลงนามเห็นอะไร

ลายมือชื่อ**ไม่ได้คำนวณสดจากบัญชีผู้ใช้** แต่อ่านจาก `signature.signature_confirmation` ที่
snapshot ชื่อไว้ ณ เวลาลงนาม ถ้าผู้ใช้เปลี่ยนชื่อภายหลัง เอกสารที่ลงนามแล้วต้องไม่เปลี่ยนตาม

การเรนเดอร์ทำ**นอก** transaction ตามแบบเดียวกับ `dataset-requests.ts`: มันคุยกับ LibreOffice
และเขียน object storage ซึ่งใช้เวลาเป็นวินาที (transaction timeout ปกติของ Prisma คือ 5 วินาที)
ถ้าขั้นนี้ล้ม การลงนามที่บันทึกไปแล้วต้องไม่ถูกย้อน — หลักฐานอยู่ใน `signature_confirmation`
เรียบร้อยแล้ว และเอกสารสร้างซ้ำได้จากหลักฐานนั้นเสมอ คำตอบของ API มี `agreementRendered`
บอกว่ารอบนั้นสร้างสำเร็จหรือไม่

**A0 ที่เก่ากว่า template ที่เผยแพร่อยู่จะถูกสร้างใหม่ให้เอง** ตอนเปิด
`GET /:id/legal-documents` เคสที่ต้องกันคือ หน่วยงานสร้าง PDF จาก v1 แล้วนำส่ง ต่อมามีการ
เผยแพร่ v2 ถ้าไม่สร้างใหม่ ผู้มีอำนาจจะอ่านข้อความของ v1 แต่ระบบบันทึกว่ายอมรับ v2

## 6 · การลงนามอยู่ใน `POST /:id/review` ไม่ใช่ endpoint ใหม่

`review` ยังเป็นจุดตัดสินใจเดียวของทุกด่านตามที่ `CLAUDE.md` กำหนด สองด่านสุดท้ายเพิ่ม
`signature` เข้าไปใน body:

```json
{
  "action": "approve",
  "signature": {
    "acknowledgedVersionIds": ["<A0 version>", "<A1>", "<A2>", "<A3>"],
    "confirmationText": "ข้าพเจ้าได้อ่านและเข้าใจ…"
  }
}
```

`acknowledgedVersionIds` เป็น version id ไม่ใช่รหัส `A0`/`A1` เพราะสิ่งที่ต้องบันทึกคือยอมรับ
**ฉบับไหน** และมันปิดช่องแข่งกันเองด้วย: ถ้าฝ่ายกฎหมายเผยแพร่ฉบับใหม่ระหว่างที่ผู้อนุมัติเปิด
หน้าอยู่ id ที่ส่งกลับมาจะไม่ตรงกับที่เผยแพร่ ระบบตอบ 400 `documents_not_acknowledged`
พร้อมบอกให้โหลดหน้าใหม่ แทนที่จะรับการลงนามบนข้อความที่เขาไม่ได้อ่านไว้

`confirmationText` คือข้อความจริงที่แสดงตอนกดลงนาม เก็บลง
`signature_confirmation.confirmation_text` — ถ้าเก็บแค่ "ลงนามแล้ว" แล้ววันหนึ่งข้อความนี้ถูกแก้
หลักฐานเก่าจะเปลี่ยนความหมายตามไปด้วย

ผลที่บันทึก:

| ด่าน | `signature_confirmation` | `legal_acceptance` |
|---|---|---|
| `ORGANIZATION_APPROVAL` | 1 แถว (`ORGANIZATION_APPROVAL`) | 1 แถวต่อเอกสาร ผูกกับ confirmation นั้น |
| `BDI_FINAL_APPROVAL` | 1 แถว (`BDI_FINAL_APPROVAL`) | **ไม่มี** |

`legal_acceptance` คือ "ใครยอมรับเอกสารฉบับใด" ซึ่งคือหน่วยงานผู้ลงทะเบียน การลงนามของ BDI
เป็นการเห็นชอบของสำนักงาน ไม่ใช่การยอมรับเงื่อนไข

นี่คือครั้งแรกที่ `legal.legal_acceptance` มีแถวจริง — การ์ด "Walk Demo Journeys and Fix Bugs"
บันทึกไว้ว่าตารางนี้ยังว่างเพราะยังไม่มี `legal_document_version` ให้อ้างถึง

## 6.1 · ยืนยันว่าอ่านแล้วก่อนกด "เห็นชอบ"

ผู้มีอำนาจกระทำการแทนต้องติ๊ก **"ข้าพเจ้าได้อ่านเอกสารฉบับนี้ครบถ้วนแล้ว"** ของแต่ละฉบับก่อน
ปุ่ม "เห็นชอบ" จึงกดได้ ติ๊กแล้วเก็บเป็นหลักฐานจริง ไม่ใช่แค่ปลดล็อกปุ่ม:

| คอลัมน์ | ค่า |
|---|---|
| `legal_acceptance.acceptance_method` | `CHECKBOX` |
| `legal_acceptance.accepted_at` | เวลาที่ติ๊ก**ของฉบับนั้น** ไม่ใช่เวลาที่กดลงนามตอนท้าย |
| `legal_acceptance.acceptance_context_json` | `{"attestationText": "…"}` ข้อความจริงที่แสดงตอนติ๊ก |

### ทำไมไม่วัดว่าเลื่อนอ่านถึงท้ายเอกสารแล้วหรือยัง

เป็นข้อเสนอแรกและลองทำจริงแล้ว แต่ถอยออกมา

หน้าเว็บอ่านตำแหน่งการเลื่อนข้างใน `<iframe>` ที่ข้าม origin ไม่ได้ และแม้จะ origin เดียวกัน
ตัวอ่าน PDF ของเบราว์เซอร์ก็เป็นปลั๊กอินที่ไม่เปิดสถานะการเลื่อนให้หน้าที่ฝังมันอยู่ ถ้าจะวัด
ต้องเลิกใช้ตัวอ่านของเบราว์เซอร์แล้ววาดเอกสารเองด้วย pdf.js

ลองแล้ว ตัวประตูทำงานถูกทุกกรณี (ยังไม่เลื่อน/ครึ่งทาง = กดไม่ได้ · ถึงท้าย = กดได้ ·
เปลี่ยนฉบับ = ต้องเลื่อนใหม่) แต่ pdf.js **วาดหน้าเปล่าออกมา** — พื้นขาวทึบทั้งแผ่น
ไม่มีตัวอักษรแม้ตัวเดียว (นับพิกเซลแล้ว: ทึบ 268,400 จุด ไม่ขาว 0 จุด) และ
`disableFontFace: true` ซึ่งเป็นทางแก้มาตรฐานของอาการนี้ก็ไม่ช่วย

ที่ทำให้ตัดทิ้งไม่ใช่ว่าแก้ต่อไม่ได้ แต่เป็น**ลักษณะของความล้มเหลว: มันเงียบ** ประตูที่บอกว่า
"เลื่อนถึงท้ายแล้ว" วางอยู่บนตัวอ่านที่อาจโชว์หน้าเปล่าโดยไม่แจ้งอะไร จะปล่อยให้คนเลื่อนถึงท้าย
ของความว่างเปล่าแล้วลงนามในข้อตกลงทางกฎหมาย — แย่กว่าไม่มีประตู เพราะมันผลิตหลักฐานว่า
อ่านแล้วขึ้นมาเองทั้งที่ไม่มีการอ่านเกิดขึ้น

และการวาดเองยังทำให้เสียเครื่องมือของตัวอ่านเบราว์เซอร์ทั้งชุด — ค้นหาข้อความ เลือกคัดลอก
ย่อ/ขยาย สั่งพิมพ์ ซึ่งบนเอกสารกฎหมายคือสิ่งที่คนอ่านจริงต้องใช้ บวกกับต้องเพิ่ม dependency,
worker chunk, บันเดิล legacy และ polyfill ของ `Promise.withResolvers`

การติ๊กยืนยันแลกกันตรง ๆ: มันไม่ได้พิสูจน์ว่าอ่าน (การเลื่อนก็ไม่ได้พิสูจน์ — ลากสกรอลบาร์
ครั้งเดียวก็ถึงท้าย) แต่มันคือ**การกระทำที่ผู้ลงนามตั้งใจทำ** เก็บเป็นหลักฐานได้ตรงไปตรงมา
และไม่ต้องแลกกับความสามารถของตัวอ่านเอกสาร

ถ้าวันหนึ่งต้องวัดการเลื่อนจริง ๆ ทางที่สะอาดคือ render หน้าเอกสารเป็นรูปภาพฝั่ง server
(ใช้ gotenberg ที่มีอยู่แล้ว) แล้วแสดงในกล่องเลื่อนของเราเอง — ฟอนต์อยู่ที่ server จึงไม่มี
อาการวาดหน้าเปล่า แลกกับพื้นที่เก็บรูปต่อเวอร์ชันและการเลือกคัดลอกข้อความที่หายไป

## 6.2 · เส้นทางลงทะเบียนชุดข้อมูล (A4 แบบนำส่งข้อมูล)

การ์ด **Dataset Registration PDF render** ทำให้เส้นทาง C เดินทางเดียวกับเส้นทาง B
โครงโค้ดสะท้อนกันตัวต่อตัว: `lib/dataset-document.ts` คู่กับ `lib/organization-agreement.ts`
และ `lib/dataset-values.ts` คู่กับ `lib/legal-values.ts`

**เอกสารฉบับเดียว** — A4 เท่านั้น ผนวก A1–A3 อยู่ใน scope ของการลงทะเบียนหน่วยงาน และ
หน่วยงานยอมรับไปแล้วครั้งเดียวตอนจดทะเบียน ไม่ต้องยอมรับซ้ำต่อชุดข้อมูล (ตัดสินไว้ 2026-08-20)

**A4 แทน PDF ที่ระบบวาดเอง** เหมือนที่ A0 แทนของเส้นทาง B — `renderDatasetRegistrationForm()`
กับไฟล์ `lib/pdf.ts` ทั้งไฟล์ถูกลบออก และ dependency `pdfkit` กับฟอนต์ที่มีไว้ให้มันก็ถูกถอด
ตามไปด้วย ตอนนี้ไม่มีเอกสารไหนในระบบที่โค้ดวาดเองอีกแล้ว

**ช่องติ๊ก** เป็นกลไกใหม่ที่เส้นทางนี้ต้องใช้ A4 เป็นแบบฟอร์มที่มีตัวเลือกให้กา รายละเอียด
อยู่ใน `docs/18` — ระบบกาให้ตามที่ผู้กรอกเลือก ตัวเลือกทุกข้อยังพิมพ์ครบพร้อม ☑/☐
ชื่อช่องติ๊กสร้างจาก code list ใน `lib/dataset.ts` ไม่ได้ไล่เขียนมือ

**ไม่มีช่องลงนามในเอกสาร** — A4 ที่ฝ่ายกฎหมายร่างมาจบด้วยหมายเหตุ ไม่มีตารางลงนามแบบ A0
ตัดสินไว้ 2026-08-20 ว่าไม่เพิ่มให้ หลักฐานการลงนามอยู่ใน `signature_confirmation` กับ
`legal_acceptance` และไทม์ไลน์บนหน้าจอ ตัวแปรลายมือชื่อ (`{{approver.signature}}` ฯลฯ)
ยังมีค่าให้เติมอยู่ ถ้าวันหนึ่งเพิ่มตารางลงนามเข้าไปในเอกสาร ก็ใช้ได้ทันทีโดยไม่ต้องแก้โค้ด

**ด่านที่ลงนาม** มีสองด่านเท่านั้น: `ORGANIZATION_APPROVAL` และ `BDI_FINAL_APPROVAL`
ด่านผู้เชี่ยวชาญข้อมูลกับด่านตรวจซ้ำของเจ้าหน้าที่ BDI อ่านเอกสารได้แต่ไม่ลงนาม
(การ์ดกำหนดไว้แค่สองด่านนั้น ตัดสินไว้ 2026-08-20)

**ข้อความยืนยันต่างจากเส้นทาง B** — "ยืนยันส่งแบบนำส่งข้อมูล ตามระเบียบสำนักนายกรัฐมนตรี
ว่าด้วยการแบ่งปันข้อมูลดิจิทัล พ.ศ. 2569" ตามภาพในการ์ด เพราะสิ่งที่ยืนยันคือการส่งแบบฟอร์ม
ไม่ใช่การเข้าเป็นคู่สัญญา แต่ยังต้องติ๊กยืนยันว่าอ่านครบก่อนกดยืนยันเหมือนกัน

**ไฟล์ต้นแบบยังคงร่องรอยการร่างไว้ทั้งหมด** ต่างจาก A0 — ไฮไลต์ 44 จุด ตัวอักษรสีแดง และ
คอมเมนต์ของ Word ยังอยู่ครบตามที่ตัดสินไว้ 2026-08-20 ว่าให้คงไฟล์ตามที่ฝ่ายกฎหมายร่างมา
เอกสารที่หน่วยงานลงนามจึงมีแถบไฮไลต์และตัวหนังสือสีแดงติดมาด้วย

## 7 · หน้าจอ

| หน้า | สิ่งที่เปลี่ยน |
|---|---|
| ตรวจสอบก่อนนำส่ง | แสดงเอกสารทั้งสี่ฉบับเป็นแท็บ ไม่ใช่แบบฟอร์มที่ระบบวาดเองฉบับเดียว |
| รายละเอียดคำขอ | การ์ด "เอกสารข้อตกลง" แทนการ์ด "แบบฟอร์มที่ระบบสร้าง" |
| ผู้มีอำนาจกระทำการแทน | ปุ่ม "ผ่านการตรวจสอบ" → ขึ้นเอกสารทีละฉบับ ติ๊กยืนยันว่าอ่านครบก่อนจึงกด "เห็นชอบ" ได้ (§6.1) หรือกด "ปิด" → หน้าลงนาม |
| ผู้อนุมัติ BDI | อ่านเอกสารทั้งชุดจากหน้าหลัก แล้ว "เห็นชอบและลงนาม" ทีเดียว ไม่มีการกดเห็นชอบทีละฉบับ |

กด "ปิด" กลางทางกลับไปหน้าที่มีปุ่มส่งผลการตรวจสอบ และการเห็นชอบที่กดค้างไว้ถูกล้าง —
ยังไม่มีการลงนามเกิดขึ้น จึงไม่ควรเก็บสถานะครึ่งทางไว้
