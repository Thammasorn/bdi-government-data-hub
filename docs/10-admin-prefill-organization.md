## 1. ปัญหาที่การ์ดนี้แก้

เดิม `POST /api/admin/invitations` รับ `organizationId` ได้อยู่แล้ว แต่ **ไม่มีใครสร้าง
หน่วยงานที่มีข้อมูลจริงไว้ให้ผูกได้** — ทางเดียวคือปล่อยว่างแล้วให้ระบบสร้างหน่วยงาน
ชื่อ "หน่วยงานใหม่" ขึ้นมา

และต่อให้ผูก `organizationId` ไปแล้ว พอผู้ใช้กด "สร้างหน่วยงาน" ระบบก็ยัง
**สร้างหน่วยงานใบใหม่ให้อีกใบ** เพราะ `POST /api/organizations` มองหาคำขอเดิมจาก
`created_by` เท่านั้น หน่วยงานที่ admin เตรียมไว้จึงถูกทิ้งค้างโดยไม่มีใครใช้
ผลคือข้อ 3 ของการ์ด "ทำไปแล้วครึ่งเดียว" และข้อ 4 ทำไม่ได้เลย

## 2. ลำดับการทำงานที่ได้

```
admin   POST /api/admin/organizations {organizationCode, nameTh, ...}
        └─ organization (PENDING_REGISTRATION)          ← ยังไม่มีคำขอจดทะเบียน

admin   POST /api/admin/invitations {email, role, cid, organizationId}
        └─ user_account (PENDING) + activation_key (ISSUED) + อีเมล

ผู้ใช้   เปิดลิงก์ → ยืนยันตัวตน ThaiD → ตั้งรหัสผ่าน
        └─ user_role_assignment ผูกกับหน่วยงานนั้น → session มี organizationId

ผู้ใช้   กด "สร้างหน่วยงาน" → POST /api/organizations
        ├─ มีคำขอที่ยังไม่จบของหน่วยงานนี้อยู่แล้ว → 409 exists {requestId} → เข้าไปแก้ใบเดิม
        └─ ยังไม่มี → สร้างคำขอ DRAFT **คัดลอกข้อมูลจากแถว organization มาเป็นค่าตั้งต้น**

ผู้ใช้   ตรวจ/แก้ในฟอร์ม → นำส่ง → BDI_OFFICER_REVIEW → ORGANIZATION_APPROVAL
        → BDI_FINAL_APPROVAL → organization.status = ACTIVE
```

## 3. สิ่งที่ตัดสินไว้ (ถามแล้ว 2026-08-16)

| คำถาม | คำตอบ |
|---|---|
| ช่องไหนบังคับตอน admin สร้างหน่วยงาน | **`organizationCode` + `nameTh`** เท่านั้น — คือสองคอลัมน์ที่ฐานข้อมูลบังคับจริง ที่เหลือ nullable จึงปล่อยว่างได้ |
| สถานะเริ่มต้น การ์ดเขียนว่า "Inactive" | ใช้ **`PENDING_REGISTRATION`** ตาม Journey B ที่ทำไว้แล้ว — `INACTIVE` ในสคีมาหมายถึง "เคยใช้งานแล้วถูกปิด" (คู่กับ `deactivated_at/by`) ไม่ใช่ "ยังลงทะเบียนไม่เสร็จ" |
| ป้องกันด้วยอะไร | **`x-admin-token`** เหมือน `/api/admin/*` เดิมทั้งหมด ไม่ใช่ session |
| ทำหน้าจอ admin ด้วยไหม | **ไม่ทำ** — API อย่างเดียว ตามที่ repo นี้ไม่มี admin UI มาแต่ต้น |
| `organization_code` มาจากไหน | **admin กรอกเอง** ไม่ generate ให้ (`request-number.ts` เขียนคำถามนี้ค้างไว้ตั้งแต่ตอนย้ายสคีมาแล้วว่า "ถ้าได้รหัสราชการจริงมาแล้ว ให้รับค่าจากผู้ใช้แทนการ generate") |
| แล้วในฟอร์มลงทะเบียนล่ะ | เป็นช่อง **บังคับ** ที่ prefill มาให้ ผู้ใช้แค่ตรวจและแก้ถ้าไม่ถูก |

## 4. API ที่เพิ่ม (ทั้งหมดใช้ `x-admin-token`)

```
POST  /api/admin/organizations       สร้างหน่วยงานล่วงหน้า
GET   /api/admin/organizations       รายการ · ?status= ?q=
GET   /api/admin/organizations/:id   รายละเอียด + คำขอจดทะเบียน + คำเชิญของหน่วยงานนั้น
PATCH /api/admin/organizations/:id   แก้ข้อมูล — ส่งเฉพาะช่องที่จะแก้
```

### PATCH: `null` ต่างจากไม่ส่ง

ไม่ส่ง key มา = ไม่แตะ · ส่ง `null` = ล้างค่า · `organizationCode` กับ `nameTh` ล้างไม่ได้
(NOT NULL) ส่งค่าว่างมาได้ 400

แก้ที่อยู่บางส่วนได้ — ส่งมาแค่ `subdistrict` ระบบใช้จังหวัด/อำเภอ **เดิม** ประกอบในการเทียบ
ไม่ใช่ล้างที่อยู่ทิ้งทั้งชุด และถ้าย้ายที่อยู่โดยไม่ส่ง `postalCode` มาด้วย ระบบหาให้ใหม่เอง

**การแก้หลังผู้ใช้เปิดคำขอไปแล้ว ไปไม่ถึงฟอร์มของเขา** — คำขอคัดลอกข้อมูลไปตั้งแต่ตอนเปิด
และจงใจไม่เขียนทับ (ไม่งั้นจะไปลบสิ่งที่ผู้ใช้พิมพ์ไว้) response จึงแนบ
`warning.code = "registration_in_progress"` พร้อมเลขที่คำขอนั้นมาให้ ไม่ปล่อยให้ admin
เข้าใจเอาเองว่าแก้แล้วผู้ใช้จะเห็น

### ที่อยู่รับเป็นชื่อ ไม่ใช่รหัส และ **ชื่อผิดจะถูกปฏิเสธ**

ส่ง `province` / `district` / `subdistrict` เป็นชื่อ เหมือน payload ของฟอร์มลงทะเบียน
แล้วระบบแปลงเป็นรหัสให้ **ชื่อในระบบไม่มีคำนำหน้า** — `"ดุสิต"` ไม่ใช่ `"เขตดุสิต"`

ชื่อที่เทียบไม่ได้ตอบ 400 พร้อมระบุช่อง จงใจไม่ปล่อยผ่านเป็น null เงียบ ๆ เพราะ admin
ยิง API เองไม่มี dropdown ให้เลือก ถ้าเงียบก็จะได้หน่วยงานที่ไม่มีที่อยู่ทั้งที่คนสร้าง
เชื่อว่ากรอกไปแล้ว — และ prefill ที่ควรช่วยผู้ใช้ก็หายไปด้วย

กรอกครบสามระดับแล้วไม่ต้องส่ง `postalCode` ระบบเติมให้เองเหมือนฟอร์มลงทะเบียน

### รหัสหน่วยงานซ้ำ

`organization_code` เป็น unique ทั้งตาราง — ซ้ำได้ 409 `code_exists` พร้อม `organizationId`
ของเจ้าของรหัสเดิม (ไว้ให้เรียกดูต่อได้ว่าไปชนกับหน่วยงานไหน)

ผู้ใช้แก้รหัสในฟอร์มได้ ตอน **นำส่ง** จึงตรวจซ้ำอีกรอบว่าไม่ไปชนหน่วยงานอื่น
ถ้าชนตอบ 400 ที่ช่อง `organizationCode` — ตรวจตอนนี้เพราะถ้าปล่อยไปจะไปพัง P2002
ตอนอนุมัติขั้นสุดท้าย ซึ่งเป็นคนละคนและคนละเวลา

## 5. การเติมข้อมูล (prefill) ทำตอนไหน

**ตอนผู้ใช้เริ่มลงทะเบียน ไม่ใช่ตอนออกคำเชิญ** — คัดลอกค่าจากแถว `organization` เข้าไปเป็น
snapshot ของคำขอ ณ วินาทีนั้น ถ้าคัดตั้งแต่ตอนเชิญ สิ่งที่ admin แก้หลังจากนั้นจะไม่ไปถึง
ฟอร์มของผู้ใช้เลย

ช่องที่ถูกเติมจากหน่วยงาน:

`organizationCode` · `organizationType` · ชื่อไทย · ชื่ออังกฤษ · ที่อยู่ ·
จังหวัด/อำเภอ/ตำบล · รหัสไปรษณีย์ · โทรศัพท์ · อีเมล · เว็บไซต์

ช่อง **ผู้กรอกข้อมูล** (ส่วนที่ 3 ของฟอร์ม) ถูกเติมจากบัญชีของผู้ใช้เองด้วย —
คำนำหน้า/ชื่อ/นามสกุลที่ ThaiD ยืนยันมา อีเมล เบอร์โทร และเลขบัตร ผู้ใช้แก้ได้ทั้งหมด

ชื่อ `"หน่วยงานใหม่"` (ค่า placeholder ที่ระบบตั้งเองตอนเชิญแบบไม่ระบุหน่วยงาน)
**ไม่ถูกเติม** ลงฟอร์ม เพราะไม่ใช่ข้อมูลจริง ปล่อยว่างไว้ให้ผู้ใช้พิมพ์ดีกว่าให้มาลบทิ้งก่อน

## 6. คำขอเป็นของหน่วยงาน ไม่ใช่ของคนสร้าง

`POST /api/organizations` เดิมหาคำขอที่ยังไม่จบจาก `created_by` อย่างเดียว ตอนนี้หาจาก
**`created_by` หรือ `organization_id` ของหน่วยงานที่ผู้ใช้สังกัด**

จำเป็นตั้งแต่มีคำเชิญที่ผูกหน่วยงานมาให้: หน่วยงานหนึ่งมีได้ทั้งผู้ดำเนินการและผู้มีอำนาจ
ลงนาม คนที่สองไม่ได้เป็นคนสร้างคำขอ ถ้าดูแค่ `created_by` เขาจะได้คำขอใบใหม่พร้อม
หน่วยงานใหม่ทั้งที่หน่วยงานของเขามีอยู่แล้ว — ทดสอบข้อ 6 ในข้อ 7 คุมเคสนี้ไว้

ลงฐานข้อมูลตรง ๆ แล้วเรียก `POST /api/auth/activate` ต่อ ส่วนที่ข้ามไปคือการคุยกับ
กรมการปกครอง ไม่ใช่ตรรกะของการ์ดนี้

สองเรื่องที่ SIT จับได้แล้วแก้ไปแล้ว เขียนไว้กันพลาดซ้ำ

  `toRequestData()` บันทึกลง `user_cid` — เขียนได้แต่อ่านกลับไม่ได้มาตั้งแต่ต้น เติมให้ครบแล้ว
