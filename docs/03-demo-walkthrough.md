## 1. เตรียมระบบให้พร้อม

### 1.1 สตาร์ตทุกบริการ

```bash
docker compose up -d --build
```

รอจนครบ แล้วตรวจว่าทุกอย่างเขียว:

```bash
docker compose ps
curl -s http://localhost:4000/health/ready
```

ต้องได้:

```json
{"status":"ok","checks":{"database":{"status":"up"},"storage":{"status":"up"}}}
```

ถ้า `status` เป็น `degraded` ให้ดูว่า `database` หรือ `storage` ตัวไหนล่ม แล้วดูหัวข้อ 8

### 1.2 สร้างตารางในฐานข้อมูล (ครั้งแรกเท่านั้น)

```bash
docker compose exec backend npx prisma migrate deploy
```

ถ้าขึ้น `No pending migrations` แปลว่าเคยรันไปแล้ว ข้ามได้

## 2. เลือกโหมดอีเมล

ระบบส่งอีเมล 15 แบบตามตารางใน [`01-user-journey.md` §5](01-user-journey.md)
เลือกได้ว่าจะให้ส่งจริงหรือแค่พิมพ์ลง log

### โหมด A — ไม่ส่งจริง (แนะนำตอนสาธิต)

ปล่อย `SMTP_USER` ใน `.env` ว่างไว้ ระบบจะพิมพ์เนื้ออีเมล **ลิงก์คำเชิญ** และ **รหัส OTP**
ลง log ให้แทน ไม่ต้องมีอีเมลจริง ไม่ต้องรอ inbox

เปิดหน้าต่างเทอร์มินัลไว้อีกอันเพื่อเฝ้า log:

```bash
docker compose logs -f backend | grep --line-buffered 'mail:dry-run'
```

จะเห็นแบบนี้ทุกครั้งที่ระบบ "ส่ง" อีเมล:

```
[mail:dry-run] ถึง: user.cmi@moph.go.th
[mail:dry-run] เรื่อง: คำเชิญเข้าใช้งาน Government Datahub Platform
[mail:dry-run] ลิงก์: https://bdi.thammasorn.org/activate?token=xxxxxxxx
[mail:dry-run] รหัส OTP: 048213
```

### โหมด B — ส่งจริงผ่าน Gmail

ตั้งค่าใน `.env` (ไฟล์นี้ถูก gitignore ไว้ ไม่ขึ้น repo):

```dotenv
SMTP_USER=บัญชี@gmail.com
SMTP_PASS=<App Password 16 หลัก ลบช่องว่างออก>
```

**ต้องเป็น App Password เท่านั้น** รหัสผ่าน Google ปกติใช้ไม่ได้:

1. เปิด 2-Step Verification ที่ <https://myaccount.google.com/security>
2. สร้าง App Password ที่ <https://myaccount.google.com/apppasswords>
   เลือก Mail → Other → ตั้งชื่อเช่น "BDI Datahub"
3. คัดลอกรหัส 16 หลัก **ลบช่องว่างออกให้หมด** แล้ววางใน `SMTP_PASS`

รีสตาร์ตให้ค่าใหม่มีผล:

```bash
docker compose up -d backend
```

ตรวจว่าเข้าโหมดส่งจริงแล้ว — ถ้ายังเห็นบรรทัดนี้ใน log แปลว่ายังไม่ติด:

```bash
docker compose logs backend | grep 'SMTP ยังไม่ได้ตั้งค่า'
```

ไม่มีผลลัพธ์ = ส่งจริงแล้ว

> อีเมลจาก Gmail มักตกโฟลเดอร์ **Spam/Promotions** ในการทดสอบครั้งแรก
> ถ้าไม่เห็นในกล่องหลักให้ดูที่นั่นก่อน

## 4. เดิน Journey A — Admin เชิญผู้ใช้ใหม่

สเปกระบุว่าขั้นตอนนี้ **ไม่มี UI** จึงเรียก API ตรง

> ตอนสาธิตใช้ [`../notebooks/journey-a-admin-create-user.ipynb`](../notebooks/journey-a-admin-create-user.ipynb)
> จะสะดวกกว่า — ยิงทุก endpoint ในหัวข้อนี้ทีละเซลล์ ใส่อีเมลของตัวเองได้
> และพิมพ์ทั้ง request/response ให้ผู้ชมเห็น

### ขั้นที่ 1 — ส่งคำเชิญ

```bash
source .env
curl -X POST http://localhost:4000/api/admin/invitations \
  -H "x-admin-token: $ADMIN_API_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"email":"newperson@agency.go.th","role":"ORGANIZATION_USER","cid":"1234567890121"}'
```

`role` ใส่ได้: `BDI_OFFICER` · `BDI_FINAL_APPROVER` · `BDI_DATASET_SPECIALIST` ·
`ORGANIZATION_USER` · `ORGANIZATION_APPROVER`

`cid` **บังคับ** — เป็นเลขบัตรที่จะถูกนำไปเทียบกับที่ ThaiD ส่งกลับมาตอนเปิดใช้งานบัญชี
ตอนสาธิตให้ใช้ `1234567890121` ซึ่งเป็นเลขตั้งต้นของ ThaiD sandbox

ตอบกลับ:

```json
{"invitationId":"...","email":"newperson@agency.go.th","role":"ORGANIZATION_USER",
 "roleLabel":"ผู้ใช้จากหน่วยงาน","expiresAt":"..."}
```

> API จงใจ **ไม่คืน token** กลับมา — token อยู่ในอีเมลเท่านั้น
> ถ้าเชิญอีเมลเดิมซ้ำ คำเชิญอันเก่าจะถูกยกเลิกอัตโนมัติ เหลือใช้ได้อันเดียวเสมอ

### ขั้นที่ 2 — หาลิงก์เปิดใช้งานบัญชี

**โหมด A (ไม่ส่งจริง)** — ดึงจาก log:

```bash
docker compose logs backend --tail 200 \
  | grep -A2 'ถึง: newperson@agency.go.th' | grep 'ลิงก์:'
```

**โหมด B (ส่งจริง)** — เปิดอีเมลแล้วกดปุ่ม "เปิดใช้งานบัญชี"

### ขั้นที่ 3 — ยืนยันตัวตนด้วย ThaiD

เปิดลิงก์ในเบราว์เซอร์ จะเห็นหน้า **ยืนยันตัวตนด้วย ThaiD** ซึ่งบอกไว้ล่วงหน้าว่าระบบจะเทียบ
เลขบัตรที่ได้จาก ThaiD กับเลขที่เจ้าหน้าที่บันทึกไว้ (โชว์ 4 ตัวท้ายให้ดูว่าเป็นบัตรใบไหน)

กด **ยืนยันตัวตนด้วย ThaiD** แล้วเบราว์เซอร์จะออกไปที่หน้าของกรมการปกครอง
บน sandbox หน้านั้นให้ **แก้เลขประจำตัวประชาชนได้** — นั่นคือวิธีสาธิตทั้งสองกรณี:

- ใส่เลขเดียวกับที่เชิญไว้ → กลับมาที่ระบบพร้อมข้อความยืนยันสำเร็จ
- ใส่เลขอื่น → ระบบปฏิเสธ **และยกเลิกลิงก์ทิ้งทันที** (เปิดลิงก์เดิมซ้ำจะขึ้น
  "ลิงก์คำเชิญนี้ถูกยกเลิกแล้ว") ต้องขอลิงก์ใหม่ ตามที่สเปกกำหนดไว้

เข้าหน้านี้จากหน้า login ก็ได้ — กด **กรอก Activation Key** แล้ววางคีย์จากอีเมล

### ขั้นที่ 4 — สร้างบัญชีผู้ใช้

ยืนยันตัวตนผ่านแล้วจะกลับมาที่หน้า **สร้างบัญชีผู้ใช้** พร้อมชื่อจาก ThaiD เติมไว้ให้

1. ช่อง **อีเมล** ล็อกไว้แก้ไม่ได้ (กันคำเชิญถูกใช้ผิดคน)
2. เลือก **คำนำหน้า** ตรวจ **ชื่อ / นามสกุล** ที่เติมมาจากบัตร
3. กรอก **เบอร์โทรศัพท์** — ต้องขึ้นต้น `0` และมี 9–10 หลัก
4. ตั้ง **รหัสผ่าน** — อย่างน้อย 8 ตัว มีทั้งตัวอักษรและตัวเลข
5. กด **เปิดใช้งานบัญชี**

ลองผิดดูได้: ใส่รหัสผ่านสั้น ๆ แล้วกดส่ง จะเห็น error ใต้ช่องพร้อม toast เตือน

### ขั้นที่ 5 — เข้าสู่ระบบครั้งถัดไป

เปิดใช้งานบัญชีเสร็จระบบล็อกอินให้เลย ครั้งต่อ ๆ ไปเข้าได้สองทาง

**ทาง 1 — รหัสผ่าน + OTP ทางอีเมล**

กรอกอีเมลกับรหัสผ่าน ระบบจะยังไม่ให้เข้า แต่ส่งรหัส 6 หลักไปที่อีเมลก่อน หาได้จาก:

```bash
docker compose logs backend --tail 40 | grep 'รหัส OTP'
```

กรอกลงช่อง 6 กล่อง (วางทั้งชุดทีเดียวได้) ครบ 6 หลักระบบส่งให้อัตโนมัติ ไม่ต้องกดปุ่ม

- รหัสอายุ 10 นาที
- ผิดได้ 5 ครั้ง เกินนั้นต้องกดขอใหม่
- ปุ่มขอรหัสใหม่ต้องรอ 60 วินาที

**ทาง 2 — ThaiD**

กด **เข้าสู่ระบบด้วย ThaiD** แล้วยืนยันด้วยเลขบัตรใบเดิม ระบบจับคู่บัญชีจากเลขบัตร
ไม่ต้องกรอกอีเมลหรือรหัสผ่าน

ไม่มีโหมดจำลองแล้ว ทุก deployment เรียกกรมการปกครองจริง — เครื่องที่ยังไม่มี client
credentials จะได้ 501 `not_configured` ตั้งแต่กดปุ่ม ไม่ใช่ผ่านฉลุยแบบเงียบ ๆ

### ผลลัพธ์

ระบบล็อกอินให้อัตโนมัติแล้วพาไปหน้าแรกตามบทบาท:

- เจ้าหน้าที่ BDI → `/admin/organizations`
- ผู้ใช้หน่วยงาน → `/` (หน้า empty state ถ้ายังไม่มีหน่วยงาน)

ลิงก์คำเชิญ **ใช้ได้ครั้งเดียว** เปิดซ้ำจะขึ้น "ลิงก์คำเชิญนี้ถูกใช้ไปแล้ว"

## 5. เดิน Journey B — สร้างหน่วยงานจนเปิดใช้งาน

เส้นทางนี้ต้องสลับบัญชี 4 ครั้ง แนะนำให้ใช้ **หน้าต่าง incognito แยก** สำหรับแต่ละบทบาท
จะได้ไม่ต้อง log out เข้าใหม่ตลอด

### ขั้นที่ 1 — ผู้ใช้หน่วยงานกรอกและนำส่ง

เข้าสู่ระบบด้วย `newbie@moi.go.th` / `bdi12345`

1. หน้าแรกมี **ปุ่มเดียวกลางจอ**: `สร้างหน่วยงาน` (ตามสเปก เมนูอื่นถูกซ่อนหมด) — กด
2. เข้าหน้าฟอร์ม ซ้ายมือเป็น stepper 3 ขั้นบอกว่ากรอกครบหรือยัง

**ส่วนที่ 1 — ข้อมูลหน่วยงาน**
- ชื่อหน่วยงาน, ที่อยู่
- **จังหวัด → อำเภอ → ตำบล** เป็น dropdown ลูกโซ่ ต้องเลือกไล่ตามลำดับ
  (เปลี่ยนจังหวัดแล้วอำเภอกับตำบลจะถูกล้าง เพื่อไม่ให้ได้ที่อยู่ที่ไม่มีจริง)
- **รหัสไปรษณีย์เติมให้อัตโนมัติ** เมื่อเลือกตำบลครบ
- อีเมลหน่วยงาน

**ส่วนที่ 2 — ผู้มีอำนาจกระทำการแทน**
- ชื่อ ตำแหน่ง อีเมล เบอร์โทร
- **เลขบัตรประชาชน 13 หลัก** — ระบบตรวจ checksum จริง ใส่มั่วไม่ผ่าน
  เลขที่ผ่านสำหรับทดสอบ: `1101700207994`
- **แนบคำสั่งแต่งตั้ง** (บังคับ) — PDF หรือ JPG ไม่เกิน 10 MB ลากมาวางได้
- แนบคำสั่งมอบอำนาจ (ถ้ามี)

> **อีเมลในส่วนที่ 2 สำคัญมาก** ระบบจะส่งคำขอให้ลงนามไปที่อีเมลนี้ในขั้นที่ 3
> ระบบจะออกคำเชิญให้อีเมลนี้เองถ้ายังไม่มีบัญชี — ใส่อีเมลที่คุณเปิดอ่านได้จริง

**ส่วนที่ 3 — ผู้กรอกข้อมูล**
- ชื่อ ตำแหน่ง ฝ่าย/กอง/สำนัก อีเมล เบอร์โทร

3. ลองกด **บันทึกแบบร่าง** ระหว่างทาง — ปิดเบราว์เซอร์แล้วกลับมาข้อมูลยังอยู่
4. กด **ตรวจสอบและสร้าง PDF**
   - ถ้ากรอกไม่ครบ จะขึ้น **toast เตือน** พร้อมเลื่อนจอไปที่ช่องแรกที่ผิด
   - ถ้าผ่าน ระบบสร้าง PDF จาก template แล้วพาไปหน้าตรวจสอบ
5. ดู PDF ที่ระบบสร้าง (ฝังในหน้าเลย เปิดแท็บใหม่ได้)
6. กด **นำส่งฟอร์มสร้างหน่วยงาน**

**เกิดอะไรขึ้น:** สถานะเปลี่ยนเป็น `รอตรวจสอบจาก BDI` และระบบส่งอีเมลแจ้ง
เจ้าหน้าที่ BDI **ทุกคน** แล้ว redirect มาหน้ารายละเอียดพร้อม timeline

### ขั้นที่ 2 — เจ้าหน้าที่ BDI ตรวจสอบ

เข้าสู่ระบบด้วย `officer@bdi.or.th` / `bdi12345`

1. เห็นตารางหน่วยงาน มีคอลัมน์ ชื่อหน่วยงาน · ผู้สร้าง+อีเมล · สถานะ · วันที่ยื่น
2. กรองด้วยชิปสถานะ หรือค้นหาจากชื่อ/ผู้ยื่นได้
3. คลิกแถวที่สถานะ `รอตรวจสอบจาก BDI`
4. ด้านบนมีการ์ด **"รอการพิจารณาของคุณ"** พร้อมสองปุ่ม

**ทางที่ 1 — ส่งกลับให้แก้**

กด `ต้องปรับปรุง` → modal เปิดขึ้น → พิมพ์สิ่งที่ต้องแก้ (**บังคับอย่างน้อย 10 ตัวอักษร**)
→ กดยืนยัน

สถานะเป็น `รอการแก้ไข` และส่งอีเมลพร้อมข้อความที่พิมพ์ไปหาผู้กรอก
กลับไปล็อกอินเป็นผู้ใช้หน่วยงานจะเห็นกล่องแดงบอกเหตุผล พร้อมปุ่มแก้ไข
แก้แล้วนำส่งใหม่ → กลับมาที่ `รอตรวจสอบจาก BDI`

**ทางที่ 2 — อนุมัติ**

กด `อนุมัติ` → ยืนยันใน modal

สถานะเป็น `รอตรวจสอบจากผู้มีอำนาจ` และระบบจะ:
- ถ้าอีเมลผู้มีอำนาจ **ยังไม่มีบัญชี** → สร้างคำเชิญให้อัตโนมัติ แล้วส่งลิงก์สมัคร
  (คนนั้นต้องไปเดิน Journey A ก่อน)
- ถ้ามีบัญชีแล้ว → เพิ่มสิทธิ์ให้ทันที แล้วส่งอีเมลแจ้งไปตรวจสอบ

### ขั้นที่ 3 — ผู้มีอำนาจกระทำการแทนเห็นชอบ

เข้าสู่ระบบด้วยอีเมลที่กรอกไว้ในส่วนที่ 2 — บัญชีนี้เพิ่งถูกสร้างจากคำเชิญที่ระบบส่งไปให้
(ถ้ายังไม่ได้ activate ให้ทำตามหัวข้อ 4 ก่อน)

1. เปิดหน้ารายละเอียดหน่วยงานนั้น
2. รีวิว PDF
3. กด `เห็นชอบ` → สถานะเป็น `รอ BDI ลงนาม` และแจ้งผู้อนุมัติ BDI
   (หรือ `ต้องปรับปรุง` เพื่อส่งกลับ)

### ขั้นที่ 4 — ผู้อนุมัติ BDI ลงนาม

เข้าสู่ระบบด้วย `approver@bdi.or.th` / `bdi12345`

1. เปิดรายการที่สถานะ `รอ BDI ลงนาม`
2. กด `เห็นชอบและลงนาม`

**สถานะเป็น `เปิดใช้งาน`** ระบบแจ้งทั้งผู้กรอกและผู้มีอำนาจว่าหน่วยงานพร้อมใช้งานแล้ว

### ตรวจผลงาน

เปิดหน้ารายละเอียดหน่วยงาน เลื่อนลงล่างสุดจะเห็น **ประวัติการดำเนินการ** ครบทุกขั้น
ว่าใครทำอะไรเมื่อไหร่ พร้อมข้อความที่พิมพ์ตอนส่งกลับแก้

## 6. เดิน Journey C — ขอลงทะเบียนชุดข้อมูลจนได้รับอนุมัติ

เส้นทางนี้ต้องสลับบัญชี 4–5 ครั้ง ใช้หน้าต่าง incognito แยกตามบทบาทจะสะดวกที่สุด
รายละเอียดของแต่ละด่านอยู่ใน [`01-user-journey.md` §4](01-user-journey.md)

> **เงื่อนไข**: หน่วยงานต้อง `เปิดใช้งาน` แล้ว และมีทั้งผู้ใช้และผู้มีอำนาจที่ activate บัญชีแล้ว
> ในข้อมูลตัวอย่างมีแค่ *สำนักงานสถิติแห่งชาติ* ที่ครบเงื่อนไข — ใช้ `user@nso.go.th`
> ถ้าหน่วยงานยังไม่ครบ ปุ่มจะถูก disabled พร้อมบอกว่าติดอะไร (ไม่ซ่อนปุ่ม)

### ขั้นที่ 1 — ผู้ใช้หน่วยงานกรอกและนำส่ง

เข้าสู่ระบบด้วย `user@nso.go.th` / `bdi12345`

1. เมนูบนมี **ชุดข้อมูล** — กดเข้าไปจะเห็นคำขอทั้งหมดของหน่วยงาน
   (org user **ทุกคน** ในหน่วยงานเห็นและแก้ไขได้ ไม่จำเป็นต้องเป็นคนสร้าง)
2. กด `ลงทะเบียนชุดข้อมูล` → ระบบออก **เลขที่คำขอ** `DS-REG-<ปี>-<ลำดับ>` ให้ทันที
   แล้วพาเข้าฟอร์ม 4 ส่วน (stepper ด้านซ้ายบอกว่าส่วนไหนครบแล้ว)

   | ส่วน | กรอกอะไร |
   | --- | --- |
   | 1 — ข้อมูลชุดข้อมูล | ชื่อ คำอธิบาย ประเภท หมวดหมู่ **คำสำคัญ (พิมพ์แล้วกด Enter)** ความถี่ ขอบเขต ผู้ประสานงาน |
   | 2 — วิธีการนำส่ง | API/SFTP/ฐานข้อมูล/อัปโหลดไฟล์ · รูปแบบข้อมูล · **endpoint (บังคับเมื่อเลือก API/SFTP/DB)** |
   | 3 — เงื่อนไขทางกฎหมาย | ชั้นความลับ ข้อมูลส่วนบุคคล ฐานอำนาจ สัญญาอนุญาต + **ติ๊กยอมรับเงื่อนไข** |
   | 4 — เอกสารแนบ | **พจนานุกรมข้อมูล (บังคับ)** PDF/XLSX/CSV และตัวอย่างข้อมูล (ถ้ามี) |

3. กด **บันทึกแบบร่าง** ระหว่างทางได้ ปิดเบราว์เซอร์แล้วกลับมาข้อมูลยังอยู่
4. กด **ตรวจสอบและสร้าง PDF**
   - ไม่ครบ → toast เตือน + เลื่อนจอไปช่องแรกที่ผิด
   - ผ่าน → ระบบสร้าง PDF A4 แล้วพาไปหน้า Preview ที่แสดงทั้ง PDF และไฟล์แนบ
5. กด **นำส่งคำขอ** → สถานะเป็น `รอ BDI ตรวจสอบเบื้องต้น` และ **แก้ไขไม่ได้อีก**
   ระบบส่งอีเมล + แจ้งเตือนในระบบให้เจ้าหน้าที่ BDI ทุกคน

### ขั้นที่ 2 — BDI Officer ตรวจเบื้องต้น (+ ผู้เชี่ยวชาญ)

เข้าสู่ระบบด้วย `officer@bdi.or.th` / `bdi12345` → เมนู **ชุดข้อมูล**

- กระดิ่งมุมขวาบนมีตัวเลขจำนวนที่ยังไม่อ่าน กดแล้วลิงก์ไปที่คำขอได้เลย
- เปิดคำขอ → การ์ด "รอการพิจารณาของคุณ" มีปุ่มครบชุด

**มอบหมายผู้เชี่ยวชาญ (ไม่บังคับ)** — กด `มอบหมายผู้เชี่ยวชาญ` เลือก `specialist@bdi.or.th`
ผู้เชี่ยวชาญจะได้รับอีเมล + แจ้งเตือน และเห็นคำขอนี้ในรายการของตัวเอง

สลับไปเป็น `specialist@bdi.or.th` จะทำได้สองอย่าง:

- `บันทึกความเห็น` — ขึ้นใน timeline โดย **ไม่เปลี่ยนสถานะ** (ตามสเปกที่ประสานงานนอกรอบ)
- `ต้องปรับปรุง` — ส่งกลับให้ผู้ใช้แก้ได้เองเลย

กลับมาเป็น officer แล้วเลือกทางใดทางหนึ่ง:

- `ต้องปรับปรุง` (พิมพ์อย่างน้อย 10 ตัวอักษร) → `รอการแก้ไข`
  ผู้ใช้จะเห็นกล่องแดงบอก **ว่าแก้เรื่องอะไร โดยใคร เมื่อไหร่** แก้แล้วส่งใหม่จะกลับมาด่าน 1 เสมอ
- `ส่งต่อให้ผู้มีอำนาจของหน่วยงาน` → `รอผู้มีอำนาจของหน่วยงาน`

### ขั้นที่ 3 — ผู้มีอำนาจกระทำการแทนลงนาม แล้ว BDI ตรวจซ้ำ

เข้าสู่ระบบด้วย `director@nso.go.th` / `bdi12345` (ผู้ลงนามของหน่วยงานเดียวกับคำขอ)

1. เปิดคำขอ → รีวิว PDF และไฟล์แนบ
2. กด `เห็นชอบและลงนาม` → ระบบบันทึกชื่อผู้ลงนามและเวลา (พิมพ์ลงท้าย PDF ด้วย)
   → สถานะ `รอ BDI ตรวจสอบขั้นสุดท้าย`

กลับไปเป็น `officer@bdi.or.th` → กด `ยืนยันผลการตรวจสอบ` → `รอ BDI อนุมัติ`

### ขั้นที่ 4 — ผู้อนุมัติ BDI

เข้าสู่ระบบด้วย `approver@bdi.or.th` / `bdi12345` มีสามทางเลือก:

| ปุ่ม | ผลลัพธ์ |
| --- | --- |
| `ต้องปรับปรุง` | กลับไป `รอการแก้ไข` |
| `ไม่อนุมัติ` | `ไม่อนุมัติ` — ปิดคำขอถาวร แจ้ง stakeholders ทุกคน |
| `อนุมัติ` | `อนุมัติแล้ว` — ระบบ **สร้าง PDF ฉบับสมบูรณ์ใหม่** ที่มีตราประทับอนุมัติ ผู้ลงนามทุกด่าน และวันที่ |

```bash
    order by sequence_number;"
```

- หน้ารายละเอียดล่างสุด = **ประวัติการดำเนินการ** ครบทุกด่าน พร้อมข้อความที่พิมพ์ตอนส่งกลับ
- `audit.audit_event` เก็บละเอียดกว่านั้น: ฟิลด์ที่เปลี่ยน (ก่อน/หลัง) IP และ `correlation_id`
  ที่ร้อยทุกแถวซึ่งเกิดจาก request เดียวกันเข้าด้วยกัน — ไม่แสดงบนหน้าจอโดยตั้งใจ
- PDF ฉบับอนุมัติดาวน์โหลดได้จากการ์ด "เอกสารฉบับอนุมัติ"

## 9. เปิดให้เข้าจากภายนอก (main เท่านั้น)

`main` เป็น checkout เดียวที่เปิดสู่สาธารณะ จองพอร์ต **3000 (UI)** และ **4000 (API)** ไว้เสมอ
checkout อื่นห้ามใช้สองพอร์ตนี้

| โดเมน | ชี้ไปที่ | ทำอะไร |
| --- | --- | --- |
| `bdi.thammasorn.org` | `http://localhost:3000` | หน้าเว็บ |
| `bdi-api.thammasorn.org` | `http://localhost:4000` | API |

### 9.1 ตั้งค่าฝั่งเครื่อง

```dotenv
APP_URL=https://bdi.thammasorn.org   # ใช้สร้างลิงก์ในอีเมล + เปิด Secure cookie
NEXT_PUBLIC_API_URL=                 # ปล่อยว่าง = เรียก API ที่ origin เดียวกับหน้าเว็บ
CORS_ORIGIN=https://bdi.thammasorn.org,http://localhost:3000
```

พอร์ตไม่ต้องตั้ง — `docker-compose.yml` ตรึง 3000/4000 ไว้แล้ว

**เบราว์เซอร์เรียก API ที่ origin เดียวกับหน้าเว็บเสมอ** `next.config.ts` มี rewrite ที่ส่ง
`/api/*` ต่อไปยัง backend จากฝั่ง server ของ Next ผลคือ:

- เข้าจาก `localhost:3000` → เรียก `localhost:3000/api/...`
- เข้าจาก `bdi.thammasorn.org` → เรียก `bdi.thammasorn.org/api/...`

ทั้งสองทางไม่มี CORS และ session cookie ไม่กลายเป็น cross-site

> เคยตั้ง `NEXT_PUBLIC_API_URL=https://bdi-api.thammasorn.org` แล้วพบว่า
> เปิดจาก `localhost:3000` ใช้ไม่ได้ เพราะ preflight ถูกบล็อก และต่อให้เปิด CORS ให้
> cookie ก็ยังไม่ถูกส่งอยู่ดี (คนละ registrable domain → `SameSite=Lax` ไม่ส่ง)

`bdi-api.thammasorn.org` ยังใช้ได้ตามปกติสำหรับผู้เรียก API จากภายนอก
(`CORS_ORIGIN` มีไว้เพื่อกรณีนั้น)

ตัวแปรที่เกี่ยวข้องและอย่าสับสน:

- `INTERNAL_API_URL` — ปลายทางของ rewrite ตั้งเป็น `http://backend:4000` ใน compose ไม่ต้องแก้
- `APP_URL` — ใช้ประกอบลิงก์ในอีเมล ถ้าตั้งผิดผู้ใช้จะกดลิงก์แล้วเปิดไม่ได้
- ใน compose ต้องเขียน `${NEXT_PUBLIC_API_URL-}` (ขีดเดียว) ไม่ใช่ `:-`
  เพราะ `:-` จะแทนค่าว่างด้วย default ทำให้ same-origin ไม่ทำงาน

### 9.2 รันโหมด production

**ห้ามเปิด dev server สู่สาธารณะ** — มี source map, stack trace เต็ม และ HMR ที่ไม่ทำงานผ่าน tunnel

```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build
```

ต่างจากโหมด dev ตรงที่ build เป็นบันเดิลจริง ไม่ bind-mount source เข้าไป
รันด้วย user `node` และ backend จะ `prisma migrate deploy` ให้อัตโนมัติตอนสตาร์ต

> `NEXT_PUBLIC_*` **ถูกฝังลงบันเดิลตอน build** ไม่ได้อ่านตอนรัน
> เปลี่ยนค่าเมื่อไหร่ต้อง `--build` ใหม่เสมอ ไม่งั้นเบราว์เซอร์จะยังยิงไปที่อยู่เดิม

ตรวจว่า proxy ทำงาน:

```bash
curl -o /dev/null -w '%{http_code}\n' http://localhost:3000/api/auth/me   # 401 = ถูกต้อง
```

กลับไปโหมด dev:

```bash
docker compose up -d --build
```

### 9.3 ตั้งค่าฝั่ง Cloudflare

Tunnel บนเครื่องนี้เป็นแบบ **token-managed** — คอนฟิกอยู่บน dashboard ไม่ได้อยู่ในเครื่อง
ไม่มีไฟล์ `/etc/cloudflared/config.yml` ให้แก้

ไปที่ **Zero Trust → Networks → Tunnels → tunnel ของเครื่องนี้ → Public Hostname → Add**
แล้วเพิ่มสองรายการ:

| Subdomain | Domain | Type | URL |
| --- | --- | --- | --- |
| `bdi` | `thammasorn.org` | HTTP | `localhost:3000` |
| `bdi-api` | `thammasorn.org` | HTTP | `localhost:4000` |

### 9.4 ข้อควรรู้

- **Cookie** ตั้ง `Secure` อัตโนมัติเมื่อ `APP_URL` เป็น https
  ทั้งสองโดเมนอยู่ใต้ `thammasorn.org` เดียวกันจึงนับเป็น same-site — `SameSite=Lax` ส่ง cookie
  ข้าม subdomain ได้อยู่แล้ว ไม่ต้องใช้ `SameSite=None`
- **เข้าจาก `http://localhost:3000` ใช้ได้ปกติ** เพราะ API เรียกที่ origin เดียวกัน
  (Chrome ถือว่า localhost เป็น secure context จึงรับ cookie ที่มี `Secure` ได้)
- **ตั้ง `THAID_CLIENT_ID` / `THAID_CLIENT_SECRET` ให้ครบ** ไม่งั้นปุ่ม ThaiD ตอบ 501
  และเปิดใช้งานบัญชีไม่ได้เลย (ไม่มีทางอื่นนอกจาก ThaiD)
- แนะนำให้ครอบด้วย **Cloudflare Access** ถ้ายังไม่อยากให้เปิดสาธารณะจริง ๆ

5. `ตรวจสอบและสร้าง PDF` → **โชว์ PDF ภาษาไทยที่ระบบสร้างเอง** → `นำส่งฟอร์มสร้างหน่วยงาน`
6. **เจ้าหน้าที่ BDI** (`officer@bdi.or.th`) → เปิดรายการที่ `รอตรวจสอบจาก BDI` → `อนุมัติ`
   → **กลับไปที่กล่องจดหมาย: ผู้มีอำนาจได้รับคำเชิญอัตโนมัติ** (ประโยคที่พูดค้างไว้ในองก์ที่ 1)
7. **ผู้มีอำนาจ** (`คุณ+boss@gmail.com`) เปิดลิงก์ → ลงทะเบียน + ยืนยันตัวตน → เปิดหน้าหน่วยงาน
   → รีวิว PDF → `เห็นชอบ`
8. **ผู้อนุมัติ BDI** (`approver@bdi.or.th`) → `เห็นชอบและลงนาม` → สถานะ **`เปิดใช้งาน`**
9. เลื่อนลงล่างสุด โชว์ **ประวัติการดำเนินการ** ที่บันทึกครบทุกด่าน

**ประโยคเชื่อมไปองก์ที่ 3:** ตอนนี้หน่วยงานเปิดใช้งานแล้ว และมีทั้งผู้ใช้และผู้มีอำนาจที่
เปิดบัญชีแล้ว — ครบเงื่อนไขสามข้อที่ทำให้ปุ่ม *ลงทะเบียนชุดข้อมูล* กดได้พอดี

### 10.3 องก์ที่ 3 — ลงทะเบียนชุดข้อมูล (~10 นาที)

รายละเอียดทุกช่องอยู่ในหัวข้อ 6

1. **ผู้ใช้หน่วยงาน** → เมนู **ชุดข้อมูล** (เพิ่งโผล่ขึ้นมาเพราะเงื่อนไขครบ) →
   `ลงทะเบียนชุดข้อมูล` → ระบบออก **เลขที่คำขอ `DS-REG-<ปี>-<ลำดับ>`** ให้ทันที
2. กรอกฟอร์ม 4 ส่วน — metadata · วิธีนำส่ง · เงื่อนไขทางกฎหมาย · เอกสารแนบ
   - คำสำคัญพิมพ์แล้วกด Enter
   - เลือกวิธีนำส่งเป็น API แล้วโชว์ว่า **ช่อง endpoint กลายเป็นช่องบังคับ**
   - แนบพจนานุกรมข้อมูล (บังคับ) ใช้ไฟล์ `sit-evidence/data-dictionary-sit.csv` ได้
3. `ตรวจสอบและสร้าง PDF` → หน้า Preview แสดงทั้ง PDF และไฟล์แนบ → **`นำส่งคำขอ`**
   (ย้ำว่านำส่งแล้วแก้ไม่ได้อีก)
4. **เจ้าหน้าที่ BDI** → **กดกระดิ่งมุมขวาบน** โชว์การแจ้งเตือนในระบบที่เพิ่งเด้ง →
   เข้าคำขอ → `มอบหมายผู้เชี่ยวชาญ` เลือก `specialist@bdi.or.th`
5. **ผู้เชี่ยวชาญ** (`specialist@bdi.or.th`) → `บันทึกความเห็น` →
   โชว์ว่าความเห็นขึ้น timeline **โดยไม่เปลี่ยนสถานะ** (สเปกให้ประสานงานนอกรอบ)
6. กลับเป็นเจ้าหน้าที่ → `ส่งต่อให้ผู้มีอำนาจของหน่วยงาน`
7. **ผู้มีอำนาจ** → `เห็นชอบและลงนาม` (ชื่อและเวลาถูกประทับลง PDF)
8. **เจ้าหน้าที่** → `ยืนยันผลการตรวจสอบ`
9. **ผู้อนุมัติ BDI** → `อนุมัติ` → ระบบ **สร้าง PDF ฉบับสมบูรณ์ใหม่** ที่มีตราประทับอนุมัติ
   ผู้ลงนามทุกด่าน และวันที่ → กดดาวน์โหลดให้ดู
10. ปิดท้ายด้วยสองอย่างที่อยู่คนละที่กันโดยตั้งใจ:
    - **ประวัติการดำเนินการ** บนหน้าจอ — ครบทุกด่าน ใครทำอะไรเมื่อไหร่
    - **audit log** ที่ไม่แสดงบนหน้าจอ — เก็บฟิลด์ที่เปลี่ยน (ก่อน/หลัง) และ IP

    ```bash
    docker compose exec postgres psql -U bdi -d bdi -c \
      'select action, subject_type, subject_id, ip_address, created_at
         from audit.audit_event order by created_at desc limit 10;'
    ```

    > ตาราง `activity_logs` ของเดิมถูกแทนที่ด้วย `audit.audit_event` ตอนย้ายสคีมา
    > ชื่อผู้กระทำไม่ใช่คอลัมน์อีกแล้ว แต่ถูก snapshot ไว้ใน `metadata_json`
    > เพื่อไม่ให้ log เก่าเปลี่ยนความหมายเมื่อมีคนถูกเปลี่ยนชื่อ
